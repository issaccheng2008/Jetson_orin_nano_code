# RoboCup 人形机器人 —— 现状说明

> 2026-10-03 整理。给外部专家看的，尽量只写事实和实测，不写成报告体。

## 0. 一句话

一台 **12 自由度双足人形**（双腿各 6 个关节，**没有手臂、没有头**），
在一圈 6.14m 的黑色环形赛道上跑，沿途识别 6 种几何图形卡片并做动作、跨一根红条。
**目前的状态：连一个左弯都跑不过去**——进弯那一刻视觉丢锁，之后再也没锁回来，车停在弯道中间。

## 1. 比赛规则（2026）

出处：`new_vision/docs/新赛事规则2026.md`

### 1.1 场地与赛道

| | |
|---|---|
| 场地 | 3660 × 2440 mm（`:82`） |
| 赛道 | 环形，**全长 6140 mm，宽 350 mm**（`:86`） |
| 赛道形状 | 体育场形（stadium）：两端各一个 180° 半圆 + 两段直道 |
| 中线半径 | **776 mm**（实测拟合：外边界 951、内边界 601，差 350 = 道宽，互证） |
| 限宽门 | 最窄处两条线相距 **240 mm**（规则值） |
| 障碍 | 红木条 10 × 20 mm（`:109`） |

按 776mm 中线展开：半圆弧长 `πR = 2438 mm`，直道 `(6140 − 2×2438)/2 = 632 mm`。
**赛道 79% 是弧。**

### 1.2 2026 相对 2025 的变化

- **二维码 → 6 种平面几何图形识别**（`:24`、`:70`）。2025 是 3 处二维码、20 分/处（`:74`）。
- **必须完全停止步行做动作**：动作准确且**维持 3 秒以上**；动作错 / 不足 3 秒 /
  未停稳就执行 → **计 0 分**（`:250-251`）。原地不动超 10 秒可终止（`:268`）。
- 行进竞速分从 60 提到 **200**。

### 1.3 图形卡片

10cm × 10cm 白底黑线，**线粗 0.5cm，带矩形外边框**（`:119-120`）。
6 种：圆形 / 五角星 / 正方形 / 菱形 / 十字形 / 三角形。

规则原文只列了 3 种动作（圆→举左手、五角星→举右手、正方形→抬左腿，`:206-209`），
**另外 3 种在规则里没找到**。代码里我们自己定了一套（见 §3.4）。

### 1.4 计分

行进竞速：`200 × (1 − (t − tmin)/(tmax − tmin)) × s / 614`，tmax = 4 分钟，
s 是走过的厘米数（`:244-247`）。图卡 3×20（`:234`）、越障 60（`:235`）、附加 20（`:236`）。

### 1.5 ⚠️ 一条我们没满足的硬性要求

规则 §3.1-3.2（`:146-149`）：

> 机器人必须具备明显的**头、手臂**、躯干和双足等部分……
> **整体自由度 ≥ 13 个；其中头部至少 1 个自由度，单臂至少 1 个自由度。**

**我们只有 12 个自由度，全是腿，没有头和手臂。** 这条目前不达标，是待解决的合规问题。
（其余形态要求：直立高 < 450mm、宽 < 300mm、前后 < 150mm、单腿前后弯曲自由度 ≥ 3、膝关节有明显弯曲。）

## 2. 机器人硬件

### 2.1 本体

- **12 个关节，每腿 6 个**：`pitch / roll / yaw / knee_pitch / ankle_pitch / ankle_roll`
  （`humanoid_jetson_deploy/config.py:35-48`）。**无臂、无头关节。**
- `ACTION_DIM = 12`，`OBS_DIM = 49`（`config.py:9-10`）
- ⚠️ **质量存疑**：URDF 说 ≈4.19kg，CSV 记录 ≈1.16kg，两者不一致，未确认（仓库 README:644）。
- 关节零位/符号已标定：`CALIBRATION_CONFIRMED = True`（`config.py:113-119`）；
  IMU 已标定，`IMU_TO_POLICY` 是单位阵（`config.py:127,136`）。

### 2.2 控制链路

```
USB 摄像头 ──> Jetson Orin Nano ──串口 921600──> STM32 ──> 12 个电机
                 (视觉 + ONNX 策略)               (1 kHz 电机环)
```

- 策略频率 **50 Hz**（`POLICY_DT = 0.02s`，`config.py:11-12`）
- 串口 `/dev/ttyACM0`，921600（native USB CDC，物理波特率无意义）
- 自定义帧协议：MAGIC `0xA55A`、VERSION 2、CRC-16/CCITT，
  **STM32 → Jetson 200 状态帧/s，Jetson → STM32 50 指令帧/s**（`protocol.py:14-51`）
- 三进程：A 连接器（视觉→策略中转）/ B 视觉 / C 策略

### 2.3 相机

| | |
|---|---|
| 型号 | USB UVC，`2M: 2M`（无对焦控制） |
| 分辨率/格式 | 1280×720 MJPG |
| 安装 | **高度 32.5 cm，俯角 45°**，VFOV 55.876° |
| 曝光 | `auto_exposure = 3`（全自动），白平衡也自动 |

**代码里从来没有锁过曝光。** `utils.open_camera` 只设分辨率/FOURCC
（`new_vision/jetson/utils.py:20-38`）。

## 3. 软件系统

### 3.1 视觉（Jetson，CPython）

`new_vision/jetson/line_detector_v1_warp.py`：

1. **IPM 反透视**：1280×720 → 320×400 鸟瞰图，覆盖地面 **20 ~ 80 cm**
2. 预处理：黑帽(31×31) → 自适应阈值(GAUSSIAN,31,C=−8) → 三级形态学 → 连通域掩膜
3. **两条带扫描**：低带 row 350–399（地面 **20.0–27.4 cm**）、中带 row 300–349（**27.4–34.9 cm**）
4. 逐行找两条车道边界 → 配对 → 中点
5. 融合成 `fused_err`：近带 + 前瞻带 + 曲率 + 航向角 + 左弯外推 **五项相加**，
   再加一个工程性截断（`--anticipation-clip 0.5`，PPO clip 那个意思）
6. **鸟瞰图 row 0–299（地面 35–80 cm）从不进任何带子** —— 拍到了、也做了 IPM，然后扔掉

### 3.2 控制

`new_vision/jetson/discrete_steering.py` 包住原来的连续 PID 控制器，**只替换发出去的 `wz`**：

```
err < 5cm        → wz = 0        （直走）
err ≥ 5cm        → 开一段 1.0s 的 wz = +0.5，然后强制空 2.5s 才允许下一段
```

四个参数：`--wz-fire-cm 5.0` / `--wz-turn-s 1.0` / `--wz-gap-s 2.5` / `--wz-step 0.5`。
**只有正方向（左转）**：赛道按行进方向只有左弯，反向打就是把自己往弯外推。

### 3.3 图卡识别

`new_vision/jetson/shape_detector.py`：
blackhat(核9) + 各向异性闭 + 笔画宽过滤 → Hough 双族候选 → 几何/地面正方形反投影验证
→ 帧间 IoU 跟踪 → 按 `solidity`/`fill` 分类。**纯 CV 规则法，没有训练。**

动作映射（`shape_detector.py:267-275`）：

| 形状 | 动作号 | 动作 |
|---|---|---|
| 圆形 | 1 | 举左手 |
| 五角星 | 2 | 举右手 |
| 正方形 | 3 | 抬左腿 |
| 菱形 | 4 | 抬右腿 |
| 十字形 | 5 | 举双手 |
| 三角形 | 6 | 左右摇头 |

状态机：够近 → 停车（`--card-trigger-dist-cm 43`）→ 停稳后投票（`--card-vote-frames 20`，
预算 `--card-stop-ms 3000`）→ 出事件，`--card-hold-ms 5000` 内保持。
动作 1/2/5/6 直接发 STM32；3/4 走单腿站立策略（`--one-foot-model`）。

### 3.4 参数管理

所有参数在一个 JSON 里（`line_follow_params.json`），但**实际跑车几乎全靠命令行参数**。
`new_vision/机器人上机命令与参数.md` 是操作手册（约 2400 行）。

## 4. 我们现在的策略

### 4.1 硬件给我们的设计约束（这一节是理解后面所有取舍的前提）

**这一节的话来自带队的人，我照原意记：**

> 他的关节它太小的时候会有比较大的误差，太大的时候也会有比较大的误差。
> 我们关节各个角度设计的也不是正常的机器人，它是一个非常粗糙的产品，
> 它并不能完成很精确的指令，甚至对于一些指令它都几乎不能完成。
> 对于一个确定性的指令，它表现出来的动作也没有那么的确定，他对动作的执行并不是完美的，
> 甚至可以说我让他走 20，他根本走不到 20，**他只是一个内在的参数**。
> 他每一步走他都不可能完全按照你的要求，他走的步频现在还被我们放慢了，
> 他原来的步频是 **4:8，现在是 3:8**。就是说我们即使让他抓紧转弯，他也无法抓紧转弯。
> 为什么要用 0.5 和 0.4？因为**在角度比较小的时候，它表现出来的也非常不稳定**。

翻译成设计原则：

1. **命令要少、要粗。** 想要多少量就用大档，不用"小量 + 精确时长"去凑。
2. **命令要保持到机械真的做出来。** 0.15 秒在 3:8 的步频下只有 2~3 步，
   机械还没执行完指令就变了，结果不可复现。（这是我们踩过的坑，见 §5.3）
3. **不看"指令值"，只看"上机长什么样"。** `vx = 0.2` 不等于它真走 0.2 m/s。
4. **不要堆内部判断。** 每加一个分支/计时器/阈值，都是在一个不确定的底层上再叠一层假设。

### 4.2 目标运动形状

**弯道近似多边形**（转一下、滑一段、再转一下，不是贴着曲率连续走），
**直道最多纠正两三次**。这是开环跑出来的参照：

```bash
--command-source curve --curve-vx 0.2 \
  --curve-straight-s 2 --curve-turn-s 1.5 --curve-turn-wz 0.5     # 数值是大概，还在调
```

对应到闭环：单段转向 ≤ 1 秒、两段之间 > 2 秒 —— 这两条在代码里是**硬约束**
（越界 argparse 直接拒），不是调参建议。

### 4.3 速度

`vx = 0.2 m/s`，全链路统一（B 的 `--vx`、`policy_bridge` 默认、C 的 `--max-vx` 全部 0.2）。
还有一个"步距系数"定义每 m/s 给多大步距，当前是 `0.08m / 0.3 m/s = 0.2667`。
**这些数都是待调的，不是结论。**

## 5. 现状：跑到哪一步、卡在哪

### 5.1 实车表现

从起点出发，走一段直道（视觉正常，`conf=0.98`，`err=+4.8cm` 稳定），
**进弯那一刻视觉丢锁**，之后再也没锁回来，车停下。

### 5.2 日志证据（两趟独立跑，08:39 和 09:28，完全一致）

```
[vision] 10Hz vx=+0.300 wz=+0.000 err=+4.8cm conf=0.98 ang=+23.1 lock=1 pair=1.00 pitch=45.0   ← 健康
[vision] lock lost (pair 1.00->0.00, conf 0.99->0.46) -> ~/loss_dump #1                        ← 进弯瞬间
[vision]  9Hz vx=+0.300 wz=+0.400 err=+5.1cm conf=0.46 ang=+26.4 lock=0 pair=0.00 pitch=48.6
[vision] 12Hz vx=+0.300 wz=+0.000 err=-0.6cm conf=0.41 ang=+46.2 lock=0 pair=0.00              ← err 变负
[vision] 12Hz vx=+0.300 wz=+0.000 err=-2.1cm conf=0.19 ang=-76.0 lock=0                        ← 再没纠正
[vision] 11Hz vx=+0.149 wz=+0.000 conf=0.00 lost=1                                             ← 减速停下
```

丢锁之后：`ang` 在 **±76°** 之间乱摆、`conf` 0.16~0.45、`pair` 恒为 0，
`err` 一直在负区间，而单边规则下负 `err` 一律 `wz=0` —— **一次纠正都没给。**

### 5.3 丢锁那一帧到底发生了什么（实测）

`--dump-on-loss` 存下了丢锁瞬间前后 6 帧的原图。对它们做图像统计：

| 帧 | 图像梯度（清晰度） | 最暗 10% 亮度 | 自适应阈值 |
|---|---|---|---|
| 前 5 帧（健康） | **3.42** | 91 | 80 |
| **丢锁那一帧** | **1.51** | 98 | 72 |

**一帧之内对比度掉 55%，而且各向同性**（x 方向梯度掉 0.44、y 方向掉 0.40）。
各向同性排除了运动模糊（那是有方向的），这台相机又没有对焦控制，
所以**是相机自己的输出变了**。相机是全自动曝光（`auto_exposure=3`），代码里从没锁过。

**我们试过锁手动曝光，实测得到全黑画面（均值 = 0.0），这台相机的手动曝光路径不可用。**

### 5.4 远端（35–80cm）这条路

我们做了一个诊断 `--lane-fit`：滑动窗口扫一整条高带，拟合车道中心线，
读前视 25cm 和 50cm 两处的中心，"远−近"这个量：

- **几何上分得开**：R=776mm 的弧上，50cm 处车道中心偏 18.3cm（68px），
  25cm 处只偏 4.1cm（18px），差 **−50px**；直道两端都是 0。
- **真帧上也读得出来**：18 帧真 dump 里 13 帧拟合成功，健康帧读到 −48.8px
  （几何真值 −49.8px，**差 1px**）。
- **但它救不了**：剩下 5 帧失败的全是主检测器掉锁那几帧 ——
  `--lane-fit` 的种子取自 `state["last_lane_center_x"]`，
  **它不是独立的诊断，它跟主检测器一起坏。**

### 5.5 已经排除的原因

- 不是"指令没送到"：C 侧日志确认收到 `wz=+0.400 / +0.500`。
- 不是"车没转"：IMU 积分显示那段时间它转了 **+112°**。
- 不是曝光能锁而不锁：手动曝光实测不可用。

## 6. 模型的 sim-to-real 差距

### 6.1 训练是什么

- **框架**：Isaac Sim 6.0.1.0 + Isaac Lab 3.0.0 + rsl_rl 5.4.1 + torch 2.11.0
- **检查点**：`model_850.pt`；导出 `policy.onnx`（`[batch,49] → [batch,12]`）
- **相位时钟**：训练时 `command_mode = touchdown`，部署改成 `phase_clock`，
  `control_dt = 0.02`
- **ONNX 里不含时钟**，时钟是外部给的

### 6.2 ⚠️ 已知的、写在文件里的差距

- **`hardware_validated: false`** —— 模型合同里自己标着"没在硬件上验证过"。
- **训练时的速度指令范围是 `lin_vel_x = (0.20, 0.20)`、`ang_vel_z = 0`** ——
  **转向指令在微调任务里恒为 0。** 而我们要求它做的事主要是转弯。
- 训练时 `RANDOM_STEP_DISTANCE_RANGE = (0.02, 0.12)`，默认步距 0.15。
- URDF 质量 4.19kg 与实测 1.16kg 不一致，未确认。

### 6.3 实测出来的"指令 ≠ 结果"

- **指令是"内在参数"，不是物理承诺。** 发 `vx = 0.2 m/s`，它实际走多快未知。
- **速度指令会改步态节律。** 实测：带视觉跑时把 `--vx` 默认从 0.3 改成 0.2 之后，
  **步频变快了**——降速反而加快节律。（我们一度以为"步频 = vx / 步长"，
  那是推断，被这个实测推翻。步频既不由我们设，也不独立：它跟着
  `vx` 和 `step_distance` 动。）
- 所以 `--vx` **不是纯速度旋钮**，它同时改步态节律。

### 6.4 我们最不确定的地方

1. 训练时 `ang_vel_z = 0`，**现在要它按 0.5 rad/s 转弯，是不是根本不在它的分布里？**
2. `phase_clock` 部署模式（vs 训练的 `touchdown`）在实车上到底差多少？
3. URDF 质量和实际差 3.6 倍，这个差距会不会让所有动力学相关的东西都不成立？
4. 相机全自动曝光在走路振动下频繁改变输出（§5.3），换一台能锁曝光的相机会不会有本质改善？

## 7. 我们想要什么帮助

1. **视觉丢锁**：全自动曝光的相机在走路时输出突变导致丢锁，除了换相机还有别的工程解法吗？
2. **转向控制**：在一个指令不确定、执行不精确、且训练时转向指令恒为 0 的模型上，
   做弯道跟踪，有没有比"阈值 + 固定时长一段转向"更好的、**同样简单**的做法？
3. **sim-to-real**：上面 §6.4 那四个问题，哪个是最该先查的？
4. **合规**：12 自由度纯腿不满足规则"≥13 自由度含头1臂1"，最小代价的补法是什么？

## 附录 C：这份文档里哪些是实测、哪些是推断

**实测**（有日志或图像统计支持）：
- 丢锁那一帧对比度掉 55%、各向同性 → 是相机输出变了，不是运动模糊

- `--lane-fit` 在 18 帧真图上 13 帧成功，健康帧误差 1px
