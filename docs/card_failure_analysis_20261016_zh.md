# 图卡调试报错与实车停车无识别排查（2026-10-16）

## 已修复的调试界面错误

桌面文件 `card debug error essage.txt` 中的异常是：

```text
card_debug.py, dashboard
x,y,w,h = map(int,dbg['presence_box'])
TypeError: only length-1 arrays can be converted to Python scalars
```

`ShapeDetector._observe_presence_cue()` 返回的 `presence_box` 是原图坐标下的四角点 `(4,2)` 数组，而非 `(x,y,w,h)`。界面在存在信号分支将角点数组强制转为单个整数，触发异常。现在按四边形绘制；测试也改用真实接口的数据结构，新增只有存在信号、没有分类时的回归测试。

该异常只存在于 `card_debug.py` 的画面绘制。实车入口 `run_policy_vision.py` 不调用这个 dashboard，因此它会中断独立调试程序，但不会直接导致实车分类流程跳过。

4 次失败窗口约 2.85–2.99s，`card_vote_ready=false`、`card_vote_attempts=0`、`card_vote_abstentions=0`。这表明分类没有获准开始，不是分类已运行但连续认错。成功样本的两次分类均产生有效票，并触发动作。

控制端 `humanoid_jetson_deploy/main.py` 只有在速度指令接近零且关节速度降到阈值以下时才发送重摆 action 7。原视觉端从“停车触发”开始计 3 秒超时，控制端等待站稳的 1.2–1.5 秒也消耗这段预算，给 STM32 重摆、反馈 DONE 的时间可能不足。未满足 DONE 门控时，画面即使清晰也不会调用分类器。

旧日志没有逐帧记录重摆反馈的事件号和 DONE 值，因此不能仅凭这些日志断言是 STM32 完成过晚、反馈未到、状态包被覆盖或动作未被接受中的哪一种。能确认的是上述失败窗口没有进入分类；计时预算冲突是代码和控制时间线共同支持的原因。

## 对计时的修复与后续诊断

现在保留两段有上限的等待：

1. 停车后，最多等待 `--card-stop-ms` 以观察本次新的重摆活动事件。
2. 首次看到本次活动事件后，再给重摆一个完整的 `--card-stop-ms` 完成预算，只延长一次。持续收到同一活动状态不会无限延长等待。

仍然需要“本次活动事件号匹配的 DONE → 静置 `--card-settle-ms` → 新帧分类投票”。旧事件的 DONE 不会开门，未收到 DONE 时不会猜类别。默认 3000ms 下，两段等待合计最多约 6 秒（加主循环采样误差），DONE 后另有静置和 1 秒投票窗口。

新增日志明确区分 `re-pose start timeout` 与 `re-pose completion timeout`。逐帧遥测新增等待状态、基准事件号、待完成事件号、当前反馈事件号和 DONE、剩余等待时间，后续可定位是哪道门没有通过。

独立 Debug 持续分类，而实车只在获准的停车窗口分类，这解释了为什么 Debug 能高频识别、录像中图卡也清晰，却仍然可能不执行图卡动作。

## 其余观察与验证边界

- Debug 日志也有仅存在信号的帧，部分几何候选被 `ground` 等条件拒绝，部分存在框触及画面下沿。清晰度不代表满足完整黑框和地面几何约束；但候选拒绝计数不能证明每个被拒候选就是真实卡框，不能据此贸然放宽阈值。
- 现有 Debug 测试没有填写真实标签，日志不能单独用于计算实际分类准确率。需要在同一摆位、曝光和姿态下标注后测试。
- 自动测试覆盖延迟启动、匹配 DONE 后静置、无 DONE 时有界超时，以及旧 DONE 不得开门。修复不会代替实际行走复测。
- Jetson 上已通过 132 项视觉流程测试与 30 项图卡相关测试，并成功重放 6 条真实存在框诊断数据，验证原绘制异常不再出现。
- 修复已写入磁盘，已运行的实车 Python 进程仍使用启动时加载的代码；下一次重启视觉程序后计时修复才生效。排查过程不重启正在运行的机器人服务。
