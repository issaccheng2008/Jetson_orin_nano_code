# 图卡处理 Demo：投影、二值化与停后无类别

本次只运行离线图像处理。当前分支 `policy49flitter-vi`，基于本地工作树；未修改生产图卡逻辑，未连接实车。持续单边界巡线的连续录像验证按用户要求暂缓。

## 先分清两段

| 阶段 | 程序问什么 | 实际用到的图 | 这一段失败会怎样 |
| --- | --- | --- | --- |
| 走路时 | 前面有卡吗？距离够近了吗？ | 相机原帧经 LUT 的灰度图；图卡 `selective` 找外框，另用 `ink` 找闭环；找不到完整框才用模糊 `cue` 认存在 | 不停车，后面的 `local` 根本不会运行 |
| 停车低头后 | 是六类中的哪一类？ | 先从同样的图卡候选找四角，再从灰度图矫正出整卡，做 `local` 二值和轮廓分类；失败才试旧二值分类 | 投票没有类别；整窗零票就不发 1–6 |

`contrast` 是**巡线**鸟瞰图的二值提取。下面把它拿来做离线对照，当前图卡自动流程不会读取这张图，也不会把“细线过滤后 contrast”送入图卡检测器。

走路时的停止条件还包括独立的状态闸：`presence` 已确认，当前帧有可用距离（真框用宽度，模糊 cue 用纵向位置），`card_armed` 已开放，且上一张卡的禁止重停时间已经过去。起点首卡之后的正常流程通常要求新卡先在触发线外出现，才重新武装。因此肉眼看到卡，不代表代码当前有一条能触发停车的检测记录。`local` 在这个阶段不给票，也不控制停车。

停车窗口从触发那一刻开始计 3 秒（当前默认）。先等 STM32 低头完成 DONE，再等默认 100 ms，之后每 `--card-every-stopped` 帧分类一次。当前源码 `--card-vote-frames` 默认 6；本 demo 所取的 15:16 实车记录显式配置为 20。整窗有票但凑不满目标票数，超时仍按已有票定案；**零票**则明确记录“未发送图卡类别”。

## 实际处理顺序与 45° 的含义

入口 `run_policy_vision.py` 调用 `ShapeDetector.update(frame, classify=..., issue_action=False)`，传入相机原始 BGR 帧，不传巡线鸟瞰图或巡线二值图。

1. BGR 转灰度，按实际入口配置执行 LUT，再等比缩放到 960×540。
2. `selective` 生成图卡专用二值候选；另有整图灰度 Otsu 的 `ink` 闭环支路。不是巡线 `contrast`。
3. Hough/LSD/角点/连通域/闭环产生四边形。`_quad_to_ground` 用相机高度、俯角、视场角把四角反投影到地面，`_square_on_ground` 检查尺寸、边比、对角比和内角。**这里使用 45° 等相机参数，但没有生成一张整幅鸟瞰图。**
4. 框通过后，`card_appearance.rectify_card_gray` 直接用检测出的四角，把卡片灰度矫正到 200×200。这个单应变换由四角确定，不固定为“按 45° 拉伸”。扩边 4 px 后保留外框，Otsu 分割，通过外框—纸面—内部符号的轮廓层级取图形，再调用原分类规则。
5. 局部灰度路径不给类别时，回退旧路径：`binary | ink`，四角外扩 4 px 后再内缩 14%，最近邻投影到 200×200，再闭运算/膨胀和轮廓分类。
6. 入口拿这一帧的 `shape` 投票，再发送类别事件。检测器内部 `_confirm` 的旧动作锁存不是本入口的出票闸。

因此，图卡没有沿用那张曾经近远比例不一致的旧巡线鸟瞰图。新版巡线 IPM 修复整幅地面栅格比例与覆盖范围，不能直接证明它比“由真实四角求卡片正视图”更准。**四角找错或卡框不完整，才是局部矫正的关键风险。**“原灰度”在当前配置中指未先二值化的灰度，仍已经过 LUT，并非未调光的原始灰度。

## contrast 有帮助，但要保留正确的边界

本次使用 `222f72a` 之前的真实 `line_preprocess.py` CPU 实现重放，明确不带新 5 px 细线过滤；配套当前等比例 IPM、有效地面掩膜、巡线 MAX 通道 LUT。这与图卡灰度 LUT、selective 链不同，图像对比不是只改变一个阈值的因果实验。

对 0028，contrast 的一个外环反投影回相机工作图后，通过现有图卡地面几何检查；局部灰度却返回 `no_separated_symbol`，旧二值路径也返回空。这说明这里至少有两级失败：**找框破碎，以及框内图形与外框无法独立提取**。

也有反例：0017 的 contrast 外轮廓受卡旁小标记影响，近似四角不准，地面闸拒绝；若诊断时忽略闸门，局部灰度会给菱形、旧路径给十字。0029 的残缺框也被地面闸拒绝；忽略闸门跑旧分类会得到十字。不能因为看到了清楚的二值结构，就跳过找框和几何检查。

`contrast_box_probe` 只用于诊断：先正常提取轮廓，再用人工标注 ROI 关联真实图卡进行分析。人工 ROI 不进入当前自动检测器。**它没有自动候选选择、时序确认或动作输出，不得将 probe 中类别算作自动识别成功。**

## 偏离正前方，为什么可能不出动作

当前精准分类没有“必须位于画面正中”的硬门槛。`roi_ratio=1.0` 使用整幅图；旧 `_confirm` 的横向偏离只记录软分数，且实际入口跳过 `_confirm`。不能仅凭卡偏左/偏右就归因于操作不当。

更直接的检查顺序是：

1. **低头后的卡是否完整入画。** 0029 已有直接证据。相机视野之外没有像素；移动了视点的整幅鸟瞰同样恢复不了。
2. **有效检测次数是否为零。** 当前投票等待低头 DONE，再等 100 ms；停车预算仍从停车触发时计时。若 DONE 延迟、漏掉所需 pending→done 事件，或等待占满预算，可能根本没有分类机会。这是代码上的可能路径，本次样本没有证明它就是用户所述那次的原因。
3. **有没有真实卡框。** selective 可能切碎细框，整图 Otsu 受背景亮暗分布影响。0028 的两个通道都没有完整框，不能从全图几百个 `area_max` 拒绝次数推断“真卡太大”——那些大多是场景线段组合出来的假框。
4. **四角虽有，但静态地面模型是否适用。** 停车分类窗口里代码通常固定用安装角 45°；地面反投影还没有 roll 项。偏位本身不应失败，但姿态误差、畸变、低头后的实际高度变化和错误角点都会影响地面方卡闸。
5. **已找到卡框，但是否一直没有类别。** 帧帧 `shape=None` 就是弃票，超时零票不发 1–6；票数不足目标但已有票时，当前代码仍会在超时按多数出票。因此仅增加票数或等待不能修复一直没有类别的问题。

`synthetic_geometry.csv` 是单独的理想针孔几何检查，不是实拍识别率：相机实际/假设均为 45°、无 roll 时，在完整入画的 57 组横向位置/卡片朝向/距离组合上，57 组地面几何通过。实际俯角 55°而仍假设 45°时，同网格完整入画 59 组中通过 17 组；45°且加 15° roll 时，54 组通过 38 组。它证明模型失配能够拒绝真实方卡，但这些比例不是实车发生概率，未证明实际相机误差就是 10°或 15°。

## 建议的下一步

优先把未滤细线 contrast 作为**独立的找框候选**离线比较：保留当前原图分类入口，把候选四角映射回原图，继续用完整卡片的灰度读取内图形。不要让巡线末级细线过滤删掉图卡细笔画，也不要直接把整张巡线二值图送去判六类。

测试需要同时保留“0028 找框恢复”和“0017 外轮廓误合并”这类正反例；先检查角点/外框，再检查内图形与框粘连。继续保留旧分类回退，因为 0027 当前确实依靠它读出星形。姿态与计时问题用已有对应日志单独核对，不通过取消所有几何闸来掩盖。

这次只交付 demo 和故障定位证据；未宣布 contrast 已改善整体识别率，未改分类规则、停车动作或相机配置。

## 复现

使用 OpenCV **4.10.0** 和现有 LUT 文件运行。当前默认 Python 安装的是 OpenCV 5.0.0，其 Hough 返回数组形状发生变化，与现有生产检测器的读取方式不兼容；本次通过已有独立的 OpenCV 4.10 环境回放，没有修改系统依赖或检测器。

```bash
PYTHONPATH=/tmp/robocup_photo_deps python scripts/render_card_graphics_audit.py \
  --manifest docs/card_graphics_demo_2026-10-11/inputs.json \
  --output docs/card_graphics_demo_2026-10-11
```

在已有兼容 OpenCV 4.x 的环境可去掉 `PYTHONPATH`。脚本只读图片、Git 历史和 LUT；无摄像头、网络、UDP、串口或电机入口。`inputs.json` 保存显示裁剪范围及样本来源；`results.json` 保存实际结果和代码/LUT/输入校验值。JPEG 解码、库版本和当前代码不同于当时车载进程，因此当时日志与本地回放分别列出。
