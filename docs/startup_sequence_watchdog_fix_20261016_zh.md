# 初始指令中插入 stop 的排查与修复（2026-10-16）

测试：`test_143339_576197_a5a00411`。
基线：`card_recognition_debug_20261016`，`ae0d0b6`。
修复分支：`codex/fix-startup-sequence-stop`。

## 原因与证据

本轮配置的初始序列是连续 2 秒 `vx=0.2, wz=0.1`。首卡在静止门控期间已锁存为 circle。
视觉日志第 444–452 帧全部发送该速度，`card_window=false`、`event_id=0`；不存在普通图卡停车触发。

控制 CSV 却在步骤 43–44（单调时钟约 505.807–505.847s）出现零速 `stop`，随后恢复初始速度。
第 446 帧 `read_to_publish_ms=277.6ms`，前后视觉数据包的发布时间间隔约 279ms。
初始序列为立即执行而绕过了巡线中位数窗口，没有 `steering_window` 元数据；连接器因此使用普通的
250ms 视觉看门狗，而非巡线窗口的默认 1 秒有界等待。帧间隔超限后，连接器在 50Hz 发布循环中主动补零。
`command_mode=held` 只决定平滑方式，不延长看门狗。

同样，步骤 121（507.367s）提前变为零速，直到第 453 帧约 507.531s 才发布真正的首卡停车和动作事件。
第 453 帧自身处理耗时约 429ms，导致上一条初始指令再次在正式停车包到达前过期。
所以既有序列中间的短暂停顿，也有结束交接前的超时停车。

## 修复

只在实际执行初始序列时发送布尔标记 `startup_sequence_active`。连接器校验标记，继续立即输出
初始序列的速度，同时使用现有 `--window-vision-timeout`（默认 1 秒）作为有界帧间等待。
标记在连接器输出前移除，不传给策略控制器。

每段初始指令仍立即切换，不加入中位数采样等待；序列结束后仍停车并执行静止时锁存的首卡动作。
显式零速、重摆和动作包仍立即生效；普通非窗口指令仍使用 250ms 超时。视觉持续失联时仍会停车。

## 验证与边界

- 新增测试以本轮真实发布时间间隔重现旧逻辑的超时补零；修复后 50Hz 时间线上保持连续初始指令。
- 覆盖有界超时、普通指令超时、立即换段、显式停止、图卡动作、标记校验与序列化。
- 主循环回归验证初始行走包携带标记，首卡停车动作包不再携带标记。
- Windows 在允许本机 UDP/临时文件的测试环境中通过 230 项相关测试。

本轮最后的 `FAULT: STM32 rejected shape action: status=5` 是另一个异常；协议定义 5 为 `ACTION_FAILED`。
日志显示该事件先被 accepted，之后执行失败，不能仅凭这些记录确认下位机失败原因，亦不能认定本次
看门狗修复解决了该动作故障。软件回归不替代场地实车验证。

部署需同时更新视觉端、`policy_bridge.py` 和连接器，并在下次测试前重启视觉与连接器进程。
只更新磁盘文件不会替换已运行 Python 进程中的代码。
