# 观测日志按策略维度分文件修复

2026-10-04。修复范围为`humanoid_jetson_deploy/policy_runner.py`及新增`tests/test_observation_dump.py`。未提交；没有改变模型观测、模型动作、关节目标限制或电机映射。

## 原问题

`OneFootPolicy`继承`HumanoidPolicy`，初始化时也创建`ObservationDump`。此前表头固定为walking49维，但单腿实际写46维：表头64列，数据61列。同一`POLICY_OBS_CSV`路径加载walking和onefoot时，两种行进入同一CSV，单腿后部观测与action错列。

## 修复后的文件和字段

若设置`POLICY_OBS_CSV=records/obs.csv`：

| 策略 | 实际写入文件 | 列数 | 命令观测 |
|---|---|---:|---|
| walking49 | `records/obs.csv` | 64 | vx、wz、step_distance、crossing |
| onefoot46 | `records/obs_onefoot46.csv` | 61 | lift_command |

walking保留原文件名与完整表头，已有默认调用`observation_columns()`和`open_observation_dump()`仍按49维工作。onefoot派生文件名，保留指定路径的扩展名。启动时输出`Policy observation log: <实际路径> (schema=walking49/onefoot46)`，可从控制台确定实际日志。

初始化读取现有文件表头，只在schema相同的文件中追加；schema不符会明确报错，原文件不被覆盖。append先检查obs和action维度，禁止产生错误宽度行。onefoot没有速度命令，其`cmd_is_exact_zero`留空；抬腿条件由`lift_command`列描述。walking的速度零指令标记行为不变。

既有错误CSV不会自动重写，分析时仍要按旧日志产生时的策略判断是否存在61/64列混写。此修复也不改变此前`accel_*`为模型缩放后加速度、`t_host_iso`实际上保存Unix秒的旧字段定义，避免破坏现有walking解析；这些历史命名应在后续日志schema升级时说明。

## 验证

新增6项测试验证：两种初始化顺序共用指定路径时各文件不覆盖、每行与表头长度一致、action哨兵值落在正确列、重开只追加一次表头、已有异类schema不被修改、错误宽度行不被写入、实际walking/onefoot类选对schema并报告真实路径、ENV未设置时关闭日志。

```bash
PYTHONPATH=humanoid_jetson_deploy python -m unittest discover -s humanoid_jetson_deploy/tests -p test_observation_dump.py
PYTHONPATH=humanoid_jetson_deploy python -m unittest discover -s humanoid_jetson_deploy/tests -p test_policy_runner.py
PYTHONPATH=humanoid_jetson_deploy python -m unittest discover -s humanoid_jetson_deploy/tests -p test_one_foot_policy.py
```
