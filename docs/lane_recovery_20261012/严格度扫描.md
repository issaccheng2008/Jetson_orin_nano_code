# 巡线接纳门槛：同一录像的严格度扫描

## 结论

本轮**不建议直接把 25%、50% 或 75% 设为比赛默认值**。它们确实使双边接纳数下降，但未把质量较差的帧稳定转成 `LOST`：三个中间档在 466 帧中都只有 1 帧 `LOST`。未通过双边的帧会进入单边或 `VISIBLE_ONLY`。后者只有线的方向，**没有可信的赛道中心位置**，不能算作双边或单边路径。

这是一项接纳率对照，没有逐帧赛道真值，不能由接纳数推断走得更准。50% 和 75% 的单边位置数反而比 0% 多，说明这几个百分比不是单调的“去掉坏帧”旋钮。

## 比较方式

- 录像：2026-10-12 `test_120221_007796_2d456e27/video/camera_commands.avi`；SHA-256 `bc20d535a90dc51ffcfc1273808109df7b75d35cb5048654e25e23081d6800bb`。
- 852 个录像帧按 `frames.jsonl` 的 `source_frame` 去重后为 **466 个不同源帧**，其中录像命令 `vx>0` 的 **327 帧**另列一表。
- 只取录像左侧鸟瞰原图 `(0,0,480,358)`，缩回算法栅格；沿用同一 `contrast` 二值、LUT、标定、代码默认 12 cm 缺口补线和扫描距离。已是鸟瞰图，不再做一次 IPM。这个回放设置不一定等于当时板子的配置。
- 0%=当前连续模式的宽松门槛；25/50/75%=以下数值门槛在宽松和旧严格值之间线性插值。整数门槛按代码取整。100%**切到原来的严格模式**，因为旧模式还有无法线性插值的身份时效、路径一致性和兜底开关。逐帧验证 100% 与单独调用 `strict` 的结果一致。

## 为什么中间值没有按预期增加 LOST

门槛是逐级尝试的：双边拟合失败后，会试单边拟合；单边失败后，连续模式还允许只取可见线方向。严格度变大使一部分帧从 BOTH 改判为 RIGHT_ONLY，未必拒绝。**只有 100% 切回原严格模式时**，方向兜底和其他类别开关才关闭，因此 75%→100% 有明显跳变。

即使把连续模式的所有可调数值设为旧严格值、但保留连续模式的类别开关，同视频仍得到 BOTH 246、单边 88、VISIBLE_ONLY 131、LOST 1。这个对照说明问题在接管路径，不只是数值阈值；其摘要在 `strictness_sweep/pct_100_numeric/summary.json`。

当前录像缺少人工标注的“真实左右边界、中心位置、方向”逐帧真值。下一步若要选比赛档位，应在同一批关键帧标出这三项，分别统计错线、位置偏差、方向偏差及 `VISIBLE_ONLY` 接管的风险；再单独决定哪些方向兜底帧允许进入控制。不能仅靠减少 `LOST` 或增加 BOTH 选档。保持默认 0%，直到完成该核对。

## 复现与文件

按钮配置 `config/button_start.env.example` 中 `LANE_STRICTNESS_PCT=0`；手动入口用 `--lane-observation-mode continuous --lane-strictness-pct 25` 等。100% 会显示 `effective=strict`；直接设置 `LANE_OBSERVATION_MODE=strict` 也可使用原严格模式。

```bash
PYTHONPATH=/tmp/robocup_photo_deps python scripts/replay_lane_recovery.py \
  /tmp/nano_loss_audit/test_120221_007796_2d456e27/video/camera_commands.avi \
  docs/lane_recovery_20261012/strictness_sweep/pct_025 \
  --code-root "$PWD" --mode continuous --strictness-pct 25 \
  --gap-fill --no-save-masks
```

`strictness_sweep/` 下每档的 `summary.json`、`frames.jsonl` 和 `same_frame_modes.csv` 可按源帧查状态。录像经过压缩、缩放和原录制流程处理；离线重放不是原始 USB 帧，也没有验证实车轨迹。并行离线回放中的 `process_ms` 不能用来推断 Nano 实时性能。
