# 转弯占空比分析与测试方案

适用分支：`policy49-button-test`，按钮启动、`WZ_MODE=segments` 或 `heading`。分析依据是 2026-10-08 提供的配置截图和 18:31:13–18:31:31 的服务日志。

## 1. 先说结论

你的理解正确：左右角度容忍度越小，越容易对非零方向误差发出转向命令。当前两项已经是 `0`，继续调小不能解决日志中占主要部分的“方向几何不可用”。

这次有三个不同的问题：

1. **转向档位被截住了。** `WZ_STEP=0.3` 在 `heading/segments` 中是档位上限，不是最小转向速度。即使 `MAX_WZ=0.5`，左转配置的 `0.37/0.5` 和右转的 `0.5` 也不会被选中。
2. **多数直行快照发生在方向几何丢失时。** 控制器先短暂保持上一条命令，超过 `LOST_HOLD_S` 后把角速度清零，保留已经执行的前进速度。减小容忍度不能让没有可靠方向的帧开始转弯。
3. **分段确认有低帧率问题。** 旧代码在帧间隔超过 `0.25s` 时重置确认，即使这一帧刚取得、观测年龄为零。4Hz 附近的抖动或偶尔较慢的处理会让连续三帧确认更难完成。本次改为间隔超过 `0.5s` 才打断连续性；新鲜度、几何质量检查和三帧确认仍然保留。

先更新代码，再把 `WZ_STEP` 调为 `0.5`，观察实际弯道表现。随后单独试 `LOST_HOLD_S=0.5`，评估短暂方向缺失是否是主要原因。不要一次同时改变速度、走廊和前视距离，否则难以判断哪项起作用。

转向命令的时间占比和转向强度是两件事。开启更高档位提高的是强度；它不能保证转弯占比达到 80%。80% 应作为同一弯道测试段的目标，不能用来强制机器人在直道或方向不可用时一直转。

## 2. 附件日志能说明什么

附件只有约 18 秒，而且包含首卡动作造成的停车；服务启动时间不是附件涵盖的运行时长。控制台输出稀疏、时间戳只精确到秒，因此以下是**快照比例**，不是准确的时间占空比：

| 来源 | 转弯快照 | 直行快照 | 停车快照 | 排除停车后的转弯比例 |
| --- | ---: | ---: | ---: | ---: |
| B：视觉发出的命令 | 7 | 13 | 11 | 35% |
| C：步态打印的模型输入 | 10 | 15 | 13 | 40% |

如果把停车也算入分母，B 的转弯快照比例约为 22.6%，很容易被看成“只有 20%”。B/C 异步打印，同一秒出现不同命令不能直接证明消息丢失。

更有诊断价值的是：

- B 的 13 条直行快照中，10 条标记 `geometry_lost_yaw_zero`，即缺少可靠方向后清零角速度；其中 9 条连位置观测也无效。
- 31 条打印出来的分段状态都是 `active=0`。其中只有 1 条 `anchored=1`，出现了一次 `confirming`。这说明这些快照主要处在回退到原 heading 控制的状态，但不能证明未打印的帧从未接入分段控制。
- 18:31:24–18:31:27 有持续数秒的无效观测。这种丢失不能靠把保持时间从 0.2 改到 0.5 秒彻底解决，需要结合失线截图检查相机视野和地面几何。
- 少数有方向的直行快照标记 `continue_block`。近端左偏保护可能参与其中；需要逐帧日志中的 `steering_decision=left_offset_release` 和 `steering_left_offset_confirmed` 才能确认，不能仅凭较大的远端角度认定是容忍度的问题。

没有本次相机图像，无法确认无效几何来自视野、线条质量、标定还是拟合筛选。本次没有降低图像新鲜度、宽度、锚定或分段几何连续性要求。

### 低帧率问题的软件对照

使用仓库已有的合格左弯夹具：近端方向为直，远端曲线需要左转；连续 20 帧，每帧间隔 0.3 秒、观测年龄为零，采用截图中的零容忍度和 50cm 前视，同时开放 0.5 档位。只改变确认间隔阈值：

| 确认间隔阈值 | 分段启用帧数 | 命令转弯时间 | 命令直行时间 | 移动中的转弯比例 |
| --- | ---: | ---: | ---: | ---: |
| 原值 0.25s | 0/20 | 0.0s | 5.7s | 0% |
| 修正后 0.5s | 18/20 | 5.1s | 0.6s | 89.5% |

统计不猜测末帧后的时间，因此 20 帧只计相邻间隔合计 5.7 秒。这个对照证明修正确实能让**有合格几何的低帧率弯道**进入转向；它使用固定合成观测，没有机身运动反馈，不能作为实车 89.5% 的预测，也不能解决附件中的持续几何丢失。

## 3. 参数分别控制什么

| 参数 | 当前截图 | 建议与作用 |
| --- | --- | --- |
| `WZ_MODE` | `segments` | 保持；分段合格时使用前方实际测得的目标，不合格时回退 heading |
| `WZ_STEP` | `0.3` | 第一轮改 `0.5`，允许选择更高档位；仍受 `MAX_WZ` 限制 |
| `MAX_WZ` | `0.5` | 保持，不需要为了开放现有档位继续加大 |
| `HEADING_LEFT_WZ` | `"0.3 0.37 0.5"` | 保持；左转三档。右转当前使用内置 `0.3/0.5` 档位 |
| 左右 `TOLERANCE_DEG` | `0/0` | 保持；只影响有可靠几何时的角度判定 |
| `HEADING_FULL_SCALE_DEG` | `15` | 保持；影响选择更高转向档位，不会修复失线 |
| `HEADING_CORRIDOR_CM` | `5` | 保持；它是独立的空间走廊，角度容忍度为零并不会关闭它 |
| `HEADING_LOOKAHEAD_CM` | `50` | 保持；已确认分段控制时，目标夹在实际观测范围内；分段不合格时回退 heading 的 50cm 方向投影 |
| `LOST_HOLD_S` | 未写，实际默认 `0.2` | 本次可在配置中添加。第二轮单独试 `0.5`，短暂方向缺失时多保持上一条命令 |
| `VX` | `0.2` | 前两轮保持。若图像恢复仍来不及，可第三轮单独试 `0.1` |

`LOST_HOLD_S` 保持的是上一条完整命令：原来在转弯时可能延续转弯，原来在直行时仍会延续直行。它不会创造新方向；明确标为过期的观测会立即清零角速度，即使保持时间设置为 0.5 秒。长时间缺少方向后依然会清零角速度。

原有近端左偏保护仍然保留：近端连续左偏达到阈值时，会阻止继续左转。只因为远处是左弯就豁免这一规则，可能让已经越过近边界的机器人继续向外转。本次没有采用这种修改。

## 4. Jetson 上更新与第一轮配置

终端 1：

```bash
cd ~/jetson_orin_code
git branch --show-current
git pull --ff-only

```

当前分支应为 `policy49-button-test`。在配置中只修改/添加以下值，其他参数保留原值：


命令应包含 `--wz-mode segments --lost-hold-s 0.2`，以及 `--wz-step 0.5`。本次没有改服务文件，无需重新安装服务；已有 `config/button_start.env` 不会被 `git pull` 覆盖。

## 5. 三轮对照测试

使用同一条弯道、同一入弯位置和初始朝向，每组做 2–3 次。先把“整段行走”和“弯道区间”区分开：整段中存在长直道时，总转弯占比自然会低。记录弯道起止时间，并保留对应逐帧日志和截图；下面的工具默认统计一个完整运行文件。

| 组别 | `WZ_STEP` | `LOST_HOLD_S` | `VX` | 要验证的事情 |
| --- | ---: | ---: | ---: | --- |
| A：对照 | 0.3 | 0.2 | 0.2 | 更新确认逻辑后，原配置的表现 |
| B：推荐第一轮 | 0.5 | 0.2 | 0.2 | 开放高档位后，转向强度与路线是否改善 |
| C：可选第二轮 | 0.5 | 0.5 | 0.2 | 多保留 0.3 秒能否覆盖短暂方向丢失 |

先做 A，再做 B；第 4 节给出的是 B 的配置。只有 B 仍然主要因短暂 `geometry_lost_yaw_zero` 直行时，再做 C。每次只改表中变化的一项，再重启视觉服务。

看这些指标，不只看转弯比例：

1. 弯道中 `vx>0,wz!=0` 的命令时间占比是否接近目标，以及有多少时间因方向丢失而直行。
2. 是否实际出现 `wz=+0.37/+0.5/-0.5`；出现才说明高档位参与了控制。
3. `active=1` 是否开始出现；`confirm=1/2/3` 是否能逐步增加。若始终 `anchored=0` 或 `geom=0`，应先检查失线图像，继续降角度容忍度没有作用。
4. 路线是否更贴近中线，有没有越边、来回摆动或退出弯道后仍延续旧方向。若 C 增加这些现象，恢复 `LOST_HOLD_S=0.2`。

如果 C 中仍有 1–3 秒的连续无效几何，延长保持不是主要解法。可保留 B 的其他参数、单独降 `VX=0.1` 做下一组，并结合 `records/loss_*` 图像检查当前曲线是否在相机有效视野中。没有图像依据前，不扩大新鲜度窗口或放宽几何筛选。

## 6. 统计逐帧命令时间

本分支新增一个无额外依赖的脚本。测试结束后，找到最新运行的逐帧文件：

```bash
cd ~/jetson_orin_code
find records/line_telemetry -type f -name line_frames.jsonl | sort | tail -n 5
```

选择与本次实验对应的**一个**文件；也可以对最新文件直接执行：

```bash
latest_log=$(find records/line_telemetry -type f -name line_frames.jsonl | sort | tail -n 1)
test -n "$latest_log" && .venv/bin/python new_vision/scripts/analyze_turn_duty.py "$latest_log"
```

保存完整统计结果：

```bash
test -n "$latest_log" && .venv/bin/python new_vision/scripts/analyze_turn_duty.py "$latest_log" --json > records/turn_duty_report.json
```

`moving turn` 的分母只包含前进转弯和前进直行，停车、其他命令和未知时间不计入。`duration_s` 同时展示转弯、直行、停车及未知秒数；`moving_reason_duration_s` 展示移动中各原因持续时间，`moving_segment_active_duration_s` 展示分段实际启用/回退时长。

工具按相邻帧时间戳估计前一条命令持续时间。默认超过 0.5 秒的间隔整段算 `unknown`，末帧之后不猜时长，坏行和时间回退不会直接拼接。若 unknown 很多，应先检查帧率和日志完整性，不把这些间隔补成转弯来凑比例。按单个运行文件分析，不拼接多个运行的 JSONL。

这仍是**帧间命令时长估计**：日志在处理帧时记录，网络发布和模型接收存在时间差；它不是实测机身角速度，也不是机器人已经达到 80% 的证明。

只有 journal 时，可保存日志再统计快照：

```bash
sudo journalctl -u humanoid-button-vision.service -b --since "2026-10-08 18:31:13" --until "2026-10-08 18:31:32" --no-pager > records/vision_journal.txt
.venv/bin/python new_vision/scripts/analyze_turn_duty.py records/vision_journal.txt
```

按本次实验时间替换日期和时刻。journal 报告分别展示 B/C 快照比例，不输出伪造的转弯时长。

## 7. 新增诊断与本次改动范围

视觉 console 新增 `decision`、`braked`、`geom`、`pts`、`rmse`、`near_z`；分段 console 新增 `confirm`。对应的完整诊断字段已经在逐帧 `measurement` 中，可以区分“没有方向”“等待确认”“空间保护阻止转向”和“模型最短保持”。

本次行为修改只有新鲜分段观测的连续确认间隔；新增配置项的默认值仍为原来的 `LOST_HOLD_S=0.2`。没有改变动作、反馈协议、KP/KD、下位机、0.5 秒命令最短保持或图像过期标准。软件回归覆盖新鲜低帧率确认、长间隔重置、短暂方向缺失保持、过期立即取消，以及统计器的停车/坏行/长间隔处理；硬件上的路线和占比需要上述对照测试验证。
