> 视觉侧跑在 Nano 板的 `jetson_orin_code` 仓库（`new_vision/`）里，通过 UDP 把
> `{vx, wz}` 发给走路策略。本文是**照着敲就能跑**的操作手册。
>
> 数据来源：链路与参数从代码实测（2026-09-24）；赛道几何由 1:1 渲染图与 DXF 圆弧互证。

### 记录都放 `records/`（**2026-10-03 起**）

跑一次车产出几样东西，以前散在 `~` 根下（`~/run_*.log`、`~/main_*.log`、
`~/loss_dump`、`~/shape_dump`）。现在**全部收进仓库根下的 `records/`**，
相对路径、跟仓走，`.gitignore` 里已经排除：

| 路径 | 谁写 | 内容 |
|---|---|---|
| `records/run_<时间>.log` | B（`tee`） | 视觉日志 |
| `records/main_<时间>.log` | C（`tee`） | 策略日志 |
| `records/loss_dump/` | `--dump-on-loss` | 丢锁瞬间前后 6 帧（**工具自己建目录**） |
| `records/shape_dump/` | `--shape-dump` | 图卡检测帧（**工具自己建**） |
| `records/motor_positions/` | C 的 `--position-log-dir` 默认值 | 每趟的关节/IMU CSV（**工具自己建**） |

打包发给别人：

```bash

### 相机索引会变，别写死

早期这台机器只有 `/dev/video1`、`/dev/video2`；2026-09-25 复测时 `/dev/video0` 和
`/dev/video1` 都在，实际能出图的是 **`--camera 0`**。插拔过就重新确认：

```bash
ls -l /dev/video*
for i in 0 1 2; do
  .venv/bin/python - <<EOF
import cv2
c = cv2.VideoCapture($i, cv2.CAP_V4L2)
n = sum(1 for _ in range(5) if c.read()[0]) if c.isOpened() else 0
print("index $i opened=%s 读到 %d/5 帧" % (c.isOpened(), n))
c.release()
EOF
done
```

### 串口名也会变，别写死

STM32 走 USB CDC，插拔 / 换 USB 口 / 板子重启后索引都可能变，也可能根本没枚举出来。

```bash
ls -l /dev/serial/by-id/ 2>/dev/null || echo "没有任何串口设备"
```

- **有 `usb-STMicroelectronics_...`** → STM32 在，只是索引变了。**用 `by-id` 那条路径**
  （它不随插拔变），把本文里所有 `--port /dev/ttyACM0` 换成它。
- **什么都没有** → **STM32 没枚举**，不是软件问题：
  - 换一根**能传数据的** USB 线（很多线只能充电）
  - 确认 STM32 有供电、没停在 DFU/bootloader 模式
  - `dmesg | tail -20` 看内核到底认没认到这个 USB 设备

⚠️ **`/dev/ttyACM0` 打不开时报的是 `SerialException: could not open port`**，
看起来像权限问题，其实多半是"这个设备不存在"（真正的权限问题会写 `Permission denied`，
那才需要把用户加进 `dialout` 组）。

### `git pull` 报 loose object is corrupt

```
error: inflate: data stream error (unknown compression method)
error: unable to unpack <sha> header
fatal: loose object <sha> (stored in .git/objects/xx/yyyy...) is corrupt
```

**这是板子本地仓库的对象坏了，不是远端的问题** —— 远端那份是好的，重新下一遍就行。
坏的是个 loose object（fetch 写盘时没写完整，或者卡/盘本身在抖），它在本地已经
解不开、留着只会一直挡路。

```bash
cd <仓库路径>

# 1. 先看清坏的范围，别急着删
git fsck --full 2>&1 | head -20

# 2. 删掉报出来的那些 loose object（都是远端有、能重下的）
rm .git/objects/22/80734332d97c32e2f20809fea1a7f53f229f49

# 3. 重取。--refetch 忽略本地已有对象、强制重下，比普通 fetch 可靠
git fetch --refetch origin        # git < 2.36 没这个选项，就用 git fetch origin

# 4. 确认干净了
git fsck --full 2>&1 | tail -5

# 5. 再更新。用 merge --ff-only，比 reset --hard 安全
git merge --ff-only origin/policy49
```

⚠️ **`git reset --hard` 会丢掉板子上的本地改动**，先 `git status` 看清楚；
有改动先 `git stash`。

**同一个事件往往还带一脚：工作区文件被清零。** 2026-10-02 那次就是这样 ——
`.git` 里 13 个对象写坏，同时 `main.py` / `protocol.py` / `test_protocol.py` /
`run_policy_vision.py` 四个源文件变成 **0 字节**（`git status` 里显示成"整篇删除"，
diff 头是 `index xxxxx..e69de29`，`e69de29` 就是空 blob）。这些是**已经丢了的
内容**，不是本地改动，直接恢复：

```bash
# 找出所有 0 字节的受版本控制文件
git ls-files -z | while IFS= read -r -d '' f; do
  [ -f "$f" ] && [ ! -s "$f" ] && printf '  %s\n' "$f"
done

# 从 index 恢复（这时 index 还是好的）
git checkout -- <上面列出来的文件>

git merge --ff-only origin/policy49
```

（`new_vision/jetson/__init__.py` **本来就是空的**，出现在列表里是正常的，别删。）

两次都发生在同一个时间点、盘上还有 66G 空余 —— **不是满盘**。"空文件 + 截断的
git 对象"这个组合是**不正常关机**（或存储在坏）的典型样子。碰上了先问一句
板子是不是断电/硬重启过；同一个坑连着掉两次就换盘或重新 clone 干净的一份。

⚠️ **同一块板子反复出这个问题，要怀疑存储**（SD 卡/eMMC 在坏）。偶尔一次可以当
fetch 写盘没写完；连着几次就换卡或者重新 clone 一份干净的。

## 1. 三个终端

**A — 连接器**（视觉 → 策略的中转，50Hz 零阶保持 + **斜率限制**）

```bash
python -u connector.py --vision-port 5006 --policy-port 5005 \
  --max-vx-accel 1.0 --max-wz-accel 2.0
```

`vx` 和 `wz` 都按这两个加速度上限逐拍逼近目标，**不再有阶跃**（0.4 m/s 用 0.40s、
0.5 rad/s 用 0.25s）。不写这两个参数也是同样的默认值。想对比关掉的效果就传 `1e6`。

**B — 视觉**（相机 → 巡线检测 → PID → UDP）

```bash
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless
```

真实跑（两个 dump 目录**不用换新名字也不用自己清**，启动时会自动清掉上次的）：
```bash
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless \
  --card-trigger-dist-cm 30 \
  --bias-straight-cm 0 \
  --no-red-detect \
  --wz-fire-cm 5.0 \
  --wz-turn-s 1.0 \
  --wz-gap-s 2.5 \
  --wz-step 0.5 \
  --dump-on-loss records/loss_dump \
  --shape-dump records/shape_dump \
  --max-seconds 90 2>&1 | tee records/run_$(date +%H%M%S).log
```

**离散转向的四个数全在 B 这里**（C 那边一个都不管）：

| 参数 | 默认 | 含义 | 现在的限制 |
|---|---|---|---|
| `--wz-fire-cm` | 5.0 | `err` 过多少 cm 才开一段转向 | — |
| **`--wz-turn-s`** | **1.0** | **一段转向持续多久** | **≤ 1.0（argparse 硬拒）** |
| **`--wz-gap-s`** | **2.5** | **转完之后强制滑行多久** | **> 2.0（argparse 硬拒）** |
| `--wz-step` | 0.5 | 转多猛，rad/s（不分档） | ≤ `--max-wz` |

⚠️ 后两个是**形状约束**（单段 ≤1s、间隔 >2s），超了直接报错，不是警告。
要往外调就把 `discrete_steering.py:42-43` 的 `MAX_TURN_S` / `MIN_GAP_S` 放开。

启动横幅会把生效值打出来：

```
[wz] 离散模式：wz 只有 {0, +0.5} 两个状态。err ≥ 5.0cm 就开一段 1.00s 的转向，
转完强制空 2.50s 才允许下一段（单段上限 1.0s、间隔下限 2.0s 是形状要求）。
```

**`--bias-straight-cm 0` 是有意写死的，别删 —— 它是一次对照实验，不是修好的值。**

2026-10-01 直道用的是 1。`eff = err + bias` 且 `wz` 正 = 左，所以正的直道偏置
**是在往左推**：1cm 折 `0.83 × 1 / 10 × 0.5 = 0.0415 rad/s`，3 秒约 **+7°**。
08:21 那趟直道 4.1 秒净 +19.4°（左），其中约 7° 是它贡献的。

⚠️ **代价要先知道**：环路要维持那个 `wz` 就需要固定的 `eff ≈ 3.8`，而
`eff = err + bias`，所以 bias 减小会让 **`err` 稳态值变大 = 车多往右骑**：

| bias | `err` 稳在 | 车相对车道中心 |
|---|---|---|
| 0 | +3.8 | 右 3.8cm |
| **1（旧）** | +2.8 | 右 2.8cm |
| 3.8 | 0 | 正中 |

所以改成 0 是「少 7° 左推、多 1cm 右偏」。**跑完要把这两样分开看**：
净偏航降了但右偏多了，说明方向对、量要再谈；净偏航没变，说明这 7° 不是主因，
回去查 `err` 为什么会稳在一个非零值上（见 §5 终端 B）。

**其他全是默认值，不用写。** 当前锁定：`--vx 0.2 --max-wz 0.5 --steer-full-scale-cm 10
--preview-gain 0 --bias-straight-cm 0 --bias-cm 3 --bias-gate-px 12 --bias-dead-px 6
--lost-hold-s 0.2 --deriv-pole 0.78 --card-trigger-dist-cm 43`。

⚠️ `--camera` 索引会变（§0），每次先按 §0 探测。

> **停车距离现在是一个厘米数：`--card-trigger-dist-cm`，默认 43。**
> 2026-09-28 之前写死的是 `--card-trigger-frac 0.4`（画面高度比例），两者
> 完全等价 —— **默认值没改行为，只是把"停多远"换成了能读的单位**。
> **想让它停近一点就调小这个数**：35cm → 0.491、30cm → 0.559、25cm → 0.637。
> 卡片完全在画面里能撑到约 **16cm**（再近卡片近边就出下沿了）。
> 见 §9。

> **`--bias-cm` 2026-09-26 从 5 改成"直道 1 → 弯道 3"，阀门重写成"死区 + 平滑曲率"。**
> 5cm 时直道也被拉得偏左。原因和跳变风险见 §3。

### ⚠️ 2026-10-01：误差的厘米换算被修正了，环路增益跟着变了

`err=` 那一列的**数值会变小**，这不是故障。

原来 `_px_to_ground_cm` 把鸟瞰当等距处理：横向全图用一个 `cm_per_px`，而那个值
是图**最远端**的；低带真实值只有它的 2/3。低带的误差因此被放大 **51%**，而
`fused_err_cm = smoothed_err × err_scale_cm` 正是 PID 的误差输入 —— **实际环路
增益一直比标称高 32%**。同时纵向 `z = 20 + Δy·0.1504` 假设透视是线性的，中段
偏 +11cm（z=55 处报 66.3），起跑线和红条的反投影都吃这个。

现在两样都从同一个 `M` 逐行反算（z 走红条那条精确公式，因此继承
`distance_calib` 的 0.187cm RMS）。顺带加了**车道宽锚**：赛道 350mm 是已知的，
用它把横向比例尺的绝对值在线收敛（夹在 ±20%，窄门 240mm 拖不动它）。

**这几个值要重新感受一下**（都是按老的、偏大的厘米标定的）：

| 参数 | 旧值 | 影响 |
|---|---|---|
| `--steer-full-scale-cm` | 10 | 同样的厘米数现在对应更小的像素偏差，"更硬"了 |
| `--bias-cm` / `--bias-straight-cm` | 3 / 1 | 在总误差里占的**比例**变大 |

先按 §4 跑一趟看 `err` 稳在哪，再决定动不动。

日志里新增两个量：
- `lscale=` —— 车道宽锚当前比例尺（起步 1.000，几秒内收敛，**±20% 封顶**）
- `pitch=` —— 图卡几何当前用的光轴俯角（见下）

### 机身姿态通道（B 用它修图卡几何）

**命令不用改，两端默认就是 5007 / 127.0.0.1。** C 在 `--command-source vision`
时以 10Hz 把机身的 world-down 发给 B。

想让 B 不认姿态就传 `--attitude-port 0`；C 那边同理。C 没开或没在发，B 会自动
退回配置文件里的静态安装角（**不报错、不停机**），日志里 `pitch=45.0` 就是没收到。

> 为什么只有图卡用、巡线不用：走路时俯仰以 1.7Hz 摆 30~40°，低通过的滞后值
> 描述不了当前这一帧，喂进 IPM 反而更糟；巡线靠车道宽锚定，不依赖姿态。
> 图卡是停稳了才认的，那时姿态本来就稳，3 秒停车够低通走 2.5 个时间常数。
>
> 顺带量清楚的边界：图卡的地面方形判据对俯角其实**不敏感**（20cm 处容忍
> 33~68°），机身摆动是**贴边、偶尔认不出**，不是图卡的主因。真正敏感的是
> `cy`（框中心行，25°→65° 从 434 掉到 63），那条上一版已经换成框宽了。

#### ⚠️ 但"巡线不用姿态"这条被台架实验推翻了 —— 2026-10-02

**车一步没动，只把站姿从直立换成后仰**，读数当场垮：

```
站直：  err=+8.4cm  lock=1  conf=0.98  ang=+22.4  lscale=1.009
后仰：  err +11.4 → -6.4  lock=0  conf=0.36  ang=+62.5  lscale→1.183（顶到钳位）
```

对照组（**站着不动 30 秒**）：`far=-33` 一位不变、`ang=+22.4` 不动、`lscale` 1.000→1.009
就停住 —— **所以不是相机漂移，是姿势触发的**。

分两段，都是同一个根：

| | 现象 | 机制 |
|---|---|---|
| 瞬间 | `ang` 22→45、`curve` 0→-24、`far` -33→-70、近带锁失效 | 姿势变了，几何错，检测直接垮 |
| 之后 ~15s | `err` 从 +11 走到 -6、`lscale` 1.02→1.18 | `lateral_scale`（τ≈5s）拿被姿势污染的"车道宽"重新锚定 |

而**停车做动作时机身必然后仰**（模型站姿就是后仰的），所以每次停车之后那几秒
巡线的几何都是错的 —— 这是"停车后跑出去"的直接原因。

**`--line-pitch`**（默认关）：把机身俯角也喂给巡线，但**只在停车窗口 +
`--line-pitch-hold-s`（默认 2.5s）那一段**。走路时仍旧用静态安装角 —— 上面那条
"1.7Hz 步态摆动"的理由针对的是走路，不适用于这种慢变的后仰。

> 之前那句"巡线靠车道宽锚定，不依赖姿态"要改读法：**锚定能吸收的是几何的
> 常数偏差，吸收不了姿势变化**；而且它自己就被姿势驱动，慢到 15 秒还顶钳位。

#### 台架怎么测这条：`--hold-still`

测这个必须让 C（`main.py`）跑起来 —— 姿态是它从 STM32 读了广播到 5007 的。
但 C 一开、B 这边一发 `vx=0.2`，车就走了，测不了。

**`--hold-still`**（B 的参数）：发出去的 vx/wz 一律压成 0，检测、日志、图卡那套
逻辑全都照跑。于是 C 可以正常开（姿态是活的），车原地站着 —— 也就是那个后仰的
站姿（模型的站姿本身就后仰）。

⚠️ **两个陷阱**（都踩过）：
1. **只开 B、不开 C** → 姿态收不到，`pitch=45.0` 一直不变，`--line-pitch` 变成
   逐位 no-op，白测一趟。2026-10-02 就这么白跑了一次。现在 B 启动会打
   `⚠️ --line-pitch 开着，但姿态收不到` 提醒。
2. **`--line-pitch` 和 `--hold-still` 别搞混**：前者管"巡线吃不吃俯角"，后者管
   "发不发速度"，两个都要开才测得到。

怎么看结果：直立站着不动 → 记 `err`；让它换成后仰站姿 → 再看 `err`。补偿生效的话
两次应该接近（±2cm 内），而不是像没补偿那样走 10~20cm。

### B 的两个记录开关（排查用，默认都关）

正常跑别开 —— 图卡检测本身很贵（每帧 84~120ms），落盘还会一直写磁盘。

**① 图卡的真实帧** —— 把「卡在视野里」的每一帧原图 + 那帧完整的 `card_dbg` 落盘：

```bash
cd ~/jetson_orin_code && source .venv/bin/activate
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless \
  --shape-dump records/shape_dump --max-seconds 90 2>&1 | tee records/run_$(date +%H%M%S).log
```

**② 转弯/掉锁出错的真实帧** —— 掉锁那一瞬间前后几帧，每帧两个 jpg：

```bash
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless \
  --dump-on-loss records/loss_dump --max-seconds 90 2>&1 | tee records/run_$(date +%H%M%S).log
```

两个可以一起开（再加一个 `--dump-on-loss records/loss_dump`）。

⚠️ **目录不用每次换新的，也不用自己清** —— 启动时会先把上次跑留下的 dump 删掉，
并打印 `cleared N files from the last run`。**只删本工具写的那种文件名**（`NNNN_*_gN.jpg`
和 `NNN_NN_pair*_conf*` 那一套），目录里别的东西一律不动，所以指到有别的文件的目录也安全。

> 为什么必须清：序号**每次跑都从 1 重来**。不清的话两遍跑的 `0021_cross` 和

`DRY RUN: command enable flag is OFF` 然后**一直算、不发电机**——日志看起来完全正常

| 结果 | 结论 |

## 3. 推荐值（从赛道几何推出来的，不是试出来的）

### 赛道真实几何

轨道是**体育场形**（stadium）——两端各一个 180° 半圆，其余是直道，底部中间
收窄成限宽门。

| | 半径 | 怎么量的 |
|---|---|---|
| 外边界线两端 | **951 mm** | 对 1:1 渲染图做圆拟合，残差 0.1 px |
| 内边界线两端 | **601 mm** | 同上 |
| 差 | **350 mm** | = 道宽 ✓ 互证 |
| **中线** | **776 mm ≈ 0.78 m** | (951+601)/2 |

> 两个独立来源互证：DXF 里内 R=595 ↔ 外 R=945 的两段圆弧**圆心完全重合**，
> 中线 770mm，与渲染图量出的 776mm 一致。
>
> ⚠️ 底部的限宽门处有样条拼接的**折角**，曲率随测量窗口严格成正比
> （51→104→224→525→942），是纯折角特征，**不是能开的弯**，不要按它算。

### 真正的杠杆是 `--steer-full-scale-cm`（fs）

> ⚠️ **这一节 2026-09-24 修过一次，之前全错。**

> 弯道里 `wz` 只有 **0.03 rad/s**，而需要 0.45~0.5 —— 机器人物理上转不了弯，
> 只会一直往前走。已修（检测器新增 cm 版 `fused_err_cm`，`fs` 默认 50 → 10）。

`fs` 带单位，单位就是 `steer` 的单位（cm）；只有 `steer/fs` 这个比值无量纲。

```

steer = kp·err + ki·∫err + kd·d(err)/dt + preview_gain·step_len_cm·sin(ang)

⇒ 打满舵所需误差 e ≈ 1.06 × fs
```

| fs | 打满舵所需横向误差 | 评价 |
|---|---|---|
| 15 | 16 cm | 接近车道半宽 17.5cm，转弯迟钝 |
| **9** | **9.6 cm** | **推荐起步值** |
| 6 | 6.4 cm | 更狠，直道可能开始摆 |

### 航向角离散化：`--wz-mode discrete`（**2026-10-03 起是默认**）

连续 PID 的问题是**执行端跟不上**：直道上一直在微调、弯道轨迹"有凹有凸"，
参数怎么调都差一口气。离散模式只换发出去的 `wz`：

```
err < 0                →  0        偏左，不转（滑行）
0 ≤ err < 5cm          →  0        死区，完全直走 —— 这是它最大的收益
5 ≤ err < 8cm          →  +0.4     打一发 --wz-pulse-s，然后回 0
err ≥ 8cm              →  +0.5
```

**只有三个值：`0`、`+0.4`、`+0.5`** —— 不发负的 `wz`。赛道按行进方向只有左弯，
右转永远是转过头之后的过冲，把车往弯外推。要两边都能转加 `--wz-allow-right`。

**前提是车走得笔直**（2026-10-03 用户确认，不要拿"自然漂移"去解释）。那么 `err`
只有一个来源：赛道的弯曲。直道上车道是直的 → `err=0` → 一个脉冲都不发；左弯上
车道往左拐、车继续走直线 → 车跑到中心**右**边 → `err>0` → 触发左转。

**"打一发 → 滑行 → 再打一发"就是这么来的**：左转把 `err` 纠回中心附近之后
`err` 变成负的，负的**一律不转**，车滑行；直到弯道又把它推到中心右边才打下一发。
占空比天然小于 1，不需要额外加静默段。

⚠️ **摆位**：车不能右转，所以**起点别摆在中心左侧** —— 摆偏左它没法把自己拉回来。
摆在中心或略偏右。

`--wz-mode` **默认就是 `discrete`**。要原来那套连续 PID 得显式
`--wz-mode continuous`，`SteeringController` 一个字没改，那条路逐位同以前。

```bash

python -u connector.py --max-wz-accel 0
# B（--wz-mode 现在可以不写）
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless
```

**触发看日志里的 `err=`**（原始 `fused_err_cm`）。一开始用的是加过 `--bias-*` 的
`eff=`，但**`--bias-cm` 一上来是 3.0 而当时的 `--wz-fire-cm` 也是 3.0 —— bias 自己
就把阈值顶穿了**，弯道上车正对着中心也会一直打脉冲。偏置的来历是补连续 PID 的
稳态内偏，而离散模式的阈值带本身就是那个机制，两个叠着只会双算。所以离散模式下
`--bias-cm` / `--bias-straight-cm` 不参与。

**`--wz-fire-cm` 是决定"偏左偏右"的那个参数。** 因为只能左转、且 `err>0` 才转，
车会稳定在**中心右侧 0 ~ `--wz-fire-cm` 之间**：**想更靠右就把它调大**（5 → 6 → 7）。
⚠️ 想更靠左只能调小，但没有右转把它拉回来，调太小会开始左右摆。

**别去调 `--bias-cm`** —— 它是加在 `steer` 上的，而 `steer` 在离散模式下被整个丢掉。

**`--wz-fire-cm` 是一段硬死区，不是渐变**：`|err|` 在它以内，发出去的 `wz` 是
**精确的 0**，没有 `--center-dead-cm` 那种"给一半舵"的过渡。所以"直道有多直"
完全由这一个数决定。5.0 是怎么来的：弯道稳态 `err` 实测 5~6cm，阈值设在 5 正好
卡在"弯道会触发、直道不触发"上。

`--center-dead-cm` / `--steer-full-scale-cm` / `--preview-gain` / 三项 PID 增益
同样**不起作用** —— 它们全都是往 `steer` 里加的，而 `steer` 在离散模式下被整个丢掉。
`--max-wz-right` 照旧钳负方向。

### 横向偏置：**直道 0 → 弯道 3**，阀门 2026-09-26 重写

```bash
--bias-straight-cm 0 --bias-cm 3   # 直道那半截 2026-10-01 从 1 改成 0
```

`err_有效 = err + [直道值 + (弯道值 − 直道值) × gate]`，
`gate = clamp((|curve_px_平滑| − 死区) / (满量程 − 死区), 0, 1)`

**符号（2026-10-01 当场量实）**：`wz` 正 = 左，而 `eff` 正 → `wz` 正，
所以**正偏置是把舵往左推**。1cm 折 `0.83 × 1 / 10 × 0.5 = 0.0415 rad/s`，
3 秒就是 +7° —— 08:21 那趟直道 4.1 秒净 +19.4° 里，约 7° 是它贡献的。
（当时是从"指令 `wz=+0.165` 持续 3 秒 → 陀螺仪累计 +19.4°"直接对出来的，
不是推的。）

`steer = kp × err_有效`，环稳定在 `err = eff_稳态 − 偏置`，
也就是**偏置越大，`err` 稳态值越小 = 车越靠左**。原来"直道 1 / 弯道 3" = 直道压左 1cm、
弯道压左 3cm（再早是全程 5cm）。现在直道给 0，是拿掉那 7°/3 秒的左推做对照 ——
**它不是"修好"的值，跑完要按上面那张表看代价**。

**为什么阀门必须重写：** 旧公式读的是**单帧** `curve_px`，而直道上单帧值也能抖到 18 以上
（见下面「弯道模式从来没生效过」量到的：近直段 23% 误触发）。**单帧阈值无论怎么调都分不开
直道和弯道**，所以 5cm 的偏置在直道上也吃进去一大半，车就偏左。

新阀门两处不同：

1. **读平滑值** `debug["curve_px_smooth"]`（`curve_smooth_alpha = 0.85`，≈6 帧 EMA）。
   直道的抖动**均值为 0**，弯道是**稳定的 9~14** —— 只有平均值分得开。
   实测开机第一帧的尖峰：`curve_px = −16.2` → 平滑后 `−2.4`。
2. **死区** `--bias-dead-px 6`：平滑后 `|curve_px| < 6` 时**恰好等于直道值**，
   不落在渐变中间（旧公式在 3px 时已经给了 1/4）。

#### 直道→弯道**不会跳变**

这是设计中确认过的一点，三条一起保证：

| 机制 | 每帧最多变多少 |
|---|---|
| `curve_px_smooth` 是 EMA（α=0.85） | 单帧最多走 `0.15 × Δ曲线` |
| 渐变区间 6→12px，两端差 2cm | 所以偏置每帧最多变 **≈0.9cm** |
| `connector.py --max-wz-accel` 还叠一层斜率限制 | 到串口的 `wz` 再被限一次 |

`0.9cm` 换算成 `wz` 约 `0.037 rad/s`／帧 —— 是斜坡不是阶跃。而且**总幅度只有 2cm**，
对比日志里出现过的 `err = −30cm`，量级差 15 倍，**不可能主导环路**。

真正要注意的不是跳变，是两条：

- **它是常数，不知道车到底偏了多少** —— 偏 2cm 和偏 20cm 加的是同一个值。这正是它在直道上
  误伤的原因，也是为什么现在直道给 0。
- **`--single-line-gain` 会把它一起放大**（乘在 `bias` 之后）：单线弯道上 `3 × 1.4 = 4.2cm`。
  所以**两个旋钮不要同时动**。

⚠️ 弯道 3 和死区 6 / 满量程 12 都只在一段日志上对过（直道单帧 −3~−6、弯道 9~14）。

1. **直道头几秒的净偏航**（陀螺仪积分）—— 0 应该少约 7°/3 秒

### 平滑：两层，一手治突变，一手治抖动

> 2026-09-25 加的。之前整条链路**只有 clamp，没有任何滤波**。

**第一层 — 突变**（连接器，`--max-vx-accel 1.0 --max-wz-accel 2.0`）

覆盖原本是阶跃的点：起步（0→0.4 一步到位）、Ctrl+C 停机。
丢线**已经不在这里**了 —— 控制器先在 `--lost-hold-s` 内把上一条指令淡出到 0，见 §5。

⚠️ **`--max-wz-accel 0` = 不限**（2026-10-03 加的）。这一层的存在理由是"连续指令
不该有阶跃"；`--wz-mode discrete` 要的恰恰是阶跃，短脉冲经这一削就只剩个三角形，
峰值也到不了目标（默认 2.0 时 0→0.4 要爬 0.2 秒）。跑离散就把 A 这条设成 0。
`--max-vx-accel` 不受影响，仍然要正数。

⚠️ **必须落到精确的 `0.0`**：`policy_runner.py:73` 用
`0.0 if np.all(velocity_command == 0.0) else 0.08` —— **精确浮点判等**。
渐近到 1e-9 的滤波器会让机器人"停着却一直迈 8cm 的步子"。`slew_toward` 最后一步
直接返回 target 本身，所以零是精确零。有个测试专门用反向对照盯着这条。

**第二层 — 抖动**（视觉侧，`--deriv-pole 0.78`）

实测把 `steer` 按 PID 分项拆开（真实巡线视频，cm 按真机尺度）：

| 项 | 均值 | 标准差 | **逐帧跳变 std** | 最大跳变 |
|---|---|---|---|---|
| P | 18.84 | 4.54 | 1.43 | 7.50 |
| I | 0.04 | 0.03 | 0.02 | 0.12 |
| **D（原始）** | **0.84** | **5.49** | **5.93** | **27.04** |
| 前瞻 | 0.06 | 3.44 | 2.76 | 13.65 |

**D 项均值只占 4% 有用信号，却是最大的单一噪声源。** 两个结构性原因：对已经 EMA
平滑过的信号再求差分（把残留高频放大回来），以及 `derr=(err-last_err)/dt` 里的 `dt`
是逐帧实测的（视觉帧率 10~25Hz 波动，`dt` 本身就抖 ±30%）。

治法：**3 点中值（挡单帧误检尖刺）+ 一阶低通 + 固定标称周期 0.05s**。

| `--deriv-pole` | steer 逐帧跳变 std | 降幅 | 最大跳变 |
|---|---|---|---|
| 关（旧） | 7.56 | — | 35.05 cm |
| 0（只中值） | 5.12 | −32% | 28.45 |
| 0.5 | 3.73 | −51% | 16.95 |
| **0.78（默认）** | **3.31** | **−56%** | **12.61（−64%）** |
| 0.9 | 3.17 | −58% | 12.47 |

**−56% 几乎吃满"直接删掉 D 项"那 −59% 的收益，但阻尼保住了。** 0.9 只多 2%，不划算。

## 4. 调参流程

看**终端 B** 的日志（0.5s 一条）：

```
[vision -> connector] vx=+0.400 m/s wz=+0.265 rad/s steer=+5.40cm
  err=+6.4cm err_eff=+6.4cm ang=+24.1deg curve=0 curve_px=-11(thr18) far_px=-29 conf=0.983 lost=0
```

| 字段 | 含义 |
|---|---|
| `wz` | 实际发给策略的偏航指令（rad/s）。**过弯要够 0.45，直道要接近 0** |
| `steer` | PID 输出（cm）。接近 ±10 就是打满，再大也是白搭 |
| `err` | 检测器给的横向误差（cm）。**正 = 车在车道中心的右边**（见 §5 终端 B 那张表） |
| `err_eff` | 加上 `--bias-cm` 之后、真正进 PID 的值 |
| `ang` | 拟合线角度。**曲率信号，不是"车头歪了"**（静止实测直道 -0.5°、弯道 +22°） |
| `curve_px` | 远带中心 − 近带中心。**真实弯道 9~14，直道 ≈0** |
| `conf` | 置信度。**<0.5 说明底部锁没锁上，那时的 `err` 不要信** |
| `qr` | **当前看到什么**。只在识别到的那一帧非 -1，之后回 -1——**它是一次观测，不是状态**。动作走的是 `event_id`（§9）|

| 现象 | 原因 | 改什么 |
|---|---|---|
| 过弯 `wz` 到不了 ±0.4 | fs 还没降够 | `--steer-full-scale-cm` 继续往下（9 → 7 → 6） |
| 直道 `wz` 一直在 ±0.5 来回 | 太热 | `--steer-full-scale-cm` 往上调（9 → 12 → 15） |
| 直道左右摆 | 增益太热 | 提 fs |
| 两端半圆往外甩 | 弯中 3% 饱和，最多外偏 2.4cm | 正常现象，不用管；偏得多说明 fs 没降够 |
| 弯道里车压着左线走 | 纯比例控制的稳态内偏 | `--bias-cm` 填日志里那个稳定的 `err`（如 5） |
| 直道也开始偏 | 偏置阀门开太早 | `--bias-gate-px` 往上（12 → 16 → 20） |
| 弯道转过头 | `--bias-cm` 给大了 | 减半；或 `--bias-gate-px` 往上 |
| 直道小幅高频抖动 | D 项残留噪声 | `--deriv-pole` 往上（0.78 → 0.85 → 0.9） |
| 进弯反应变钝 | D 项滤太狠 | `--deriv-pole` 往下（0.78 → 0.5 → 0） |
| 丢线时一顿一顿 | 淡出窗口太短 | `--lost-hold-s` 往上（0.2 → 0.3） |
| 丢线后反应太慢 | 淡出窗口太长 | `--lost-hold-s` 往下（0.2 → 0.1） |
| 丢线后还是往外拐 | 淡出期间转向仍有余量 | 窗口往下，或查丢线的成因（§6 第 3 条）——淡出只削窗口内的权限，不治丢线 |
| 起步/停车太猛 | 加速度上限太高 | `--max-vx-accel` 降到 0.6；转向猛就降 `--max-wz-accel` |
| 机器人朝反方向拐 | 符号反了 | `--yaw-sign` 在 -1 / 1 之间切，重启 B（默认已是 1） |
| `lost` 经常 > 0 | 丢线 | 见 §6 的第 3 条 |

**每次只改一个参数**，否则不知道是哪条起作用。

## 5. 日志怎么读

**终端 A 和 B 的日志按同一条规则排版：竖线左边是"它在干什么"，右边是"为什么"。**
只看左边就够判断跑得好不好，右边是出问题时才看的。

### 终端 B — 视觉（每 0.5 秒一行）

```
[vision]   29Hz vx=+0.400 wz=+0.133 err=+0.2cm conf=0.96 qr=-1 | steer=+2.66 eff=+2.9 ang=+15.8 curve=0/-6 far=-10 lost=0
```

| 左边（行为） | |
|---|---|
| `29Hz` | 视觉循环帧率。**图卡检测开着时会掉**，见 §9 |
| `vx` `wz` | 发给连接器的指令。**过弯看 `wz` 够不够 0.45** |
| `err` | 横向误差（cm），打的是 `fused_err_cm`。**正的 = 车在车道中心的右边**（2026-10-01 用丢锁 dump 的原始帧核过：`base_err_cm=−2.7` 那一帧，车道中心在画面中心左边 10px）。⚠️ 它和 `base_err_cm` **符号相反** —— 后者才是"车道中心相对车"的偏移（正 = 中心在车的右边） |
| `conf` | 检测置信度，**<0.15 基本算丢线** |
| `qr` | **发出去的**图卡编号。只有识别到的那一帧非 -1，之后回 -1 |
| `/ev2` | 跟在 `qr` 后面时表示事件正在持续发送（连续 5 秒），这是接收端真正用的 |

| 右边（诊断） | |
|---|---|
| `steer` | PID 输出（cm）。**到 ±10（=`fs`）就已经满舵**，不用等到 ±50。⚠️ `--wz-mode discrete` 下它**只是 PID 的对照意见**（用来核对脉冲方向对不对），实际发出去的是上面那个 `wz` —— 那里只会出现 0 / ±0.4 / ±0.5 五个值 |
| `eff` | 加上 `--bias-cm` 之后、真正进 PID 的值。**`--wz-mode discrete` 下它不参与** —— 触发看的是上面的 `err=` |
| `ang` | 拟合线角度。**曲率信号，不是"车头歪了"** |
| `curve` / `curve_px` | 弯道标志 / 曲率量。真实弯道 `curve_px` 9~14 |
| `far` | 远带误差 |
| `lost` | 连续丢线帧数。>0 时上一条指令在 `--lost-hold-s`（0.2s）内**线性淡出到 0**，不是原样重放 —— 上一条常常是只剩一条边界线时算出的饱和转向 |
| `lock` | 底锁（近带的对称配对检查）这一帧过没过。**0 = 近带被判为不对称而丢掉** |
| `pair` | 配对的点占扫过行数的比例。**0 = 整个带一个点都没出** |

| `lock` `pair` | 意思 |
|---|---|
| `lock=0` `pair=0.00` | **两个带都没出点** —— 线上真的什么都没有（全白/全黑/出画） |
| `lock=0` `pair>0` | 出点了，但**底锁判它不对称**（近带可能配错对，比如配到了另一条线） |

| `lr=01` / `lr=10` | **只看到右边线 / 只看到左边线**（赛道是内外两条黑线，中间才是跑道）。中心由缺失的那一侧按**冻结的历史实测宽度**推出 |
| `lr=00` | 一条都没看到 |

#### 单线 + 弯道 —— 2026-09-26 加

只剩一条边界时，`_infer_center_from_single_run` 把中心放在 `c ∓ w/2`。**`w` 必须是实测值**：
开机整定窗口（`startup_frames < 25`，冷启动也会重新武装）传给扫描的宽度是 **0**，
旧写法 `max(hint, min_track_width)` 会把它变成 **24px**，于是中心只离线 12px 而不是 70px ——
**偏右 19cm，直接右转**；而且这个 24 会被写回 `last_lane_width_px`，之后配对闸门
`|lane_w − 24| ≤ 80` 把真实的 140 全部拒掉，**再也回不来**。现在 0 会退回
`lane_width_init_px`(140)，且只有真的量到两条线的行才能更新宽度。

**侧别按画面中线判**（`c < img_cx` → 左线），**不是**按跟踪出来的中心。跟踪中心会漂，
一漂就把侧判错、中心再往外走、错得更牢 —— 是个正反馈环；画面中线是常量，没有回路。
余量也够：鸟瞰里赛道半宽 ≈ 70px，而最紧的实车弯（77.5cm 半径）在车前 25cm 处车道中心
只偏离中线 `25²/(2×77.5) ≈ 4cm ≈ 12px`，**70 对 12**。副作用是推出的中心被结构性限制在
中线 ±`w/2`（`w ≤ max_track_width = 300`）以内，**跑不到画面边缘** —— 旧写法那个
"clamp 到边缘当作测量"报出的 ±160px 因此不可能再出现。

单线时 `curve_px` 恒为 0（两个带推的是同一个偏移），所以 `curve_mode` 加了
「单线且 `|ang| ≥ 8°`」这一条 —— 否则 `--single-line-gain` 永远不生效。

**单线帧的 `conf` 现在 ≈0.60**（`single_line_conf 0.70` × `one_line_quality 0.85`），
原来只有 **0.127**。⚠️ **这个数不只是"可不可信"，它同时是误差 EMA 的每帧步长**
（`(1 − smooth_alpha) × conf = 0.28 × conf`）：

| | conf | 每帧步长 | 时间常数 |
|---|---|---|---|
| 正常帧（两条都看到） | ~0.99 | 0.277 | 0.23 s |
| 单线帧（**改之前**） | 0.127 | 0.036 | **1.75 s** |
| 单线帧（**现在**） | 0.595 | 0.167 | **0.37 s** |

所以 `lr=01` / `lr=10` 那些帧 `conf=0.6` 左右是**对的**，别再往回调 —— 往下调就是加滞后。
旧值那 0.127 是两层误解叠出来的：`_result_quality_weight` 里 `pair_ratio < 0.35 → ×0.80` 想罚
"该配对却配不上"，但 `pair_ratio + single_ratio ≡ 1`，它**只在真·单线帧上触发**；
再乘一个 ×0.88 的单线惩罚，合起来是给单线帧打 **0.42 折**。

**用法顺序不能颠倒**：先 `--single-line-gain 1.0` 跑一圈，确认 `lr=01` 那些帧里
`err` 的符号是往回修而不是继续往外；符号对了再上 `1.4` 左右。
**倍率是放大器不是纠正器** —— 符号反的时候加 gain 只会滑得更快。

#### ⚠️ `err` 会"稳定地错"——`conf` 不一定能报警

**`err` 大不代表检测器在抖。** 2026-09-26 实车，**车在跑、画面里没有卡片**：

```
[vision] 16Hz vx=+0.400 wz=-0.500 err=-35.9cm conf=0.78 | steer=-26.0 eff=-30.9 ang=+38.6 curve=1/-19 far=+54
```

这一行**连着四十多行（20 多秒）几乎一字不变**：`err` 只动 ±0.1cm，`wz` 全程满舵 -0.5。
另一个位置同样是跑的，稳定在 `err=+16.8`（`conf` 只有 0.4）。

车道只有 35cm 宽，半宽 17.5cm —— **-36cm 意味着"线在离车 36cm 处"，车已经在赛道外了，
不可能**。所以那不是噪声，是**锁到了别的东西**（第二条线、道边）。这种读数一旦进 PID，
`steer = kp × eff`（`eff = err + bias×闸门`，`bias` 默认 0）直接就是满舵，
**车就往反方向拐过去了**。

**判据**：看 `err` 的**绝对值**，不看它稳不稳。车道半宽 17.5cm，超了就是物理不可能。

⚠️ **对应的 `--max-lateral-cm` 默认是关的（0）。** 它一开就把读数变成"停车"，
直接改变巡线行为，而 17.5 这个阈值**还没在正常跑圈里量过**（不知道正常跑动会不会
触到它）。**要开就先量一圈**：开 `--max-lateral-cm 17.5` 跑一圈，数那行
`near band says ...` 出现几次——0 次说明没误伤，才可以把默认值改成 17.5。

`conf` 靠不住：那两次一次 0.78、一次 0.4，都在"稳定地错"。

#### ⚠️ 一帧 `conf=0.07` 就能把 `err` 打到 -30 —— 2026-09-26 修

**冷启动之后的第一个恢复帧是好的，第二帧就崩。** 左弯道 + 车前放卡：

```
[vision] 10Hz vx=+0.200 wz=+0.093 err=+1.0cm conf=0.98 | steer=+1.85 eff=+2.2 ang=+33.7 lock=1pair=1.00  ← 恢复后第 1 帧，干净
[vision] 17Hz vx=+0.400 wz=+0.483 err=+5.4cm conf=0.07 | steer=+9.66 eff=+8.4 ang=+39.5 lock=0pair=0.00  ← 第 2 帧
[vision] 16Hz vx=+0.400 wz=-0.250 err=-30.1cm conf=0.07 | steer=-28.41 eff=-25.1 ang=+48.3 curve=1/-26   ← 第 12 帧，右满舵
```

之后 20 秒都在 `±0.25~0.50` 之间左右打满（`err` 在 ±30cm 之间摆），再没锁回来。

**这不是控制的问题。** 反推那一帧：`err_scale_cm = 0.5×320×0.332 = 53.1`，
`smoothed = -30.1/53.1 = -0.567`；上一帧是 `-4.6/53.1 = -0.0866`；`smooth_alpha = 0.72` ⇒
`fused = (-0.567 + 0.72×0.0866)/0.28 = -1.80`。而四项**各自打满**才 ≈ ±1.73 ——
**说明 `near`/`far`/`angle` 同时同向顶到了饱和**（`near_err_px` 被顶到 ±160 ≈ 53cm，
车道才 35cm 宽）。控制侧是忠实地执行了一个不可能的数。

**根因：融合公式里没有 `conf`。** `fused_err` 四项全是归一化几何量，
`avg_conf` 在下面第 18 行才算出来、只拿去卡控制器 ——
**于是一帧检测器自己只给 0.07 的读数，和 0.99 的读数移动 `smoothed_err` 一样重。**

改法：`line_detector_v1_warp.py::confidence_weighted_ema()` ——
EMA 的新帧权重从 `1-alpha` 变成 `(1-alpha)×conf`。
`conf=0.99` 时权重 0.277（**和以前一样**），`conf=0.07` 时 0.0196（**小 14 倍**）。
好帧的行为一个字节都没变。

⚠️ **同一时刻还有个副作用没改**：`reset_state()` 把 `_state["startup_frames"]` 也清零了，
于是冷启动后 **25 帧内重新进入开机整定窗口**（`conf_min` 0.12→0.084、`min_weight` 0.10→0.07、
强制 simple-bottom）。卡片正好在那 25 帧里待在近带中。**这次没动它**（停完车重新放宽闸门
本身有道理），先看 `conf` 加权够不够。

**下次看**：停车恢复后头 2 秒。要求 `conf` 掉到 0.1 左右的那些帧里，
**`err` 不再跟着跳**（应该还停在个位数）。若照样跳到 ±20 以上，那条 `startup_frames` 就得一起处理。

#### ⚠️ `cy` / `cue` 必须是"这一帧"的 —— 2026-09-26 修

### ⚠️ `imu_yaw_rad` 不要用，用 `imu_gyro_z_rad_s` 积分

**`imu_yaw_rad` 是四元数解出来的 Euler 角，它自己会漂 —— 实测 8.5°/s。**
2026-10-01 跑直线（`--command-source fixed --wz 0`）时，同一趟里：

| | 净转 | 单趟内摆动 |
|---|---|---|
| `imu_yaw_rad`（Euler） | **−87.2°** | 91° |
| `imu_gyro_z_rad_s` 积分 | **−14.3°** | 40° |

**两者差值随时间单调线性增长**（3.7° → 73°，约 8.5°/s）。Euler 那条等于平均
−0.175 rad/s 转了 8.7 秒，车会明显打转、早出赛道了 —— **是它在漂，不是车在摆。**
以前拿它看出来的"车身左右乱甩 ±50°"全是伪影。

**gyro 积分怎么算：**

```bash
python -c "
import csv, math, sys
rows = list(csv.DictReader(open(sys.argv[1])))
g = 0.0; prev = float(rows[0]['elapsed_s'])
for r in rows:
    t = float(r['elapsed_s']); g += float(r['imu_gyro_z_rad_s']) * (t - prev); prev = t
print('净转 %+.1f°' % math.degrees(g))
" records/motor_positions/motor_positions_YYYYMMDD_HHMMSS_ffffff.csv
```

**这个数准到什么程度**：gyro_z 的 raw 标准差有 0.75~0.89 rad/s，看着很吓人，
但**那些摆动不是白噪声，是 ~1.7Hz 的步态周期信号**（自相关 lag1 +0.83、频谱主峰
1.65~1.73Hz + 3.4Hz 二次谐波）。**周期信号积分下来互相抵消** —— 实测把摆动滤掉
前后净转只差 **0.2° / 1.7°**。所以**净转的噪声底是 ±2°，不是 ±20°。**

（拿 `imu_yaw_rad` 的差分当判据的老写法，**在文档里已经全部换掉了**。）

- ⚠️ CSV 里**没有速度列、没有步长列**；实际前进速度和真实落脚点，整个系统都没测

## 6. 常见故障

**1. `can't open camera by index`**
相机索引会变，别写死。先跑 §0 的探测脚本确认哪个能出图（2026-09-25 复测是 `--camera 0`）。

**2. `ModuleNotFoundError: No module named 'onnxruntime'`**
**先怀疑 venv 没激活，不是没装包。** 提示符看有没有 `(.venv)`：

```bash
source .venv/bin/activate
which python        # 必须是 ~/jetson_orin_code/.venv/bin/python
```

详见 §0。这个坑 2026-09-25 踩过两次（人和 AI 各一次）。

**3. `OSError: [Errno 98] Address already in use`**
上次的 connector 没退干净：

```bash
sudo ss -lunp | grep 5006      # 看是谁
pkill -f connector.py
```

**3b. `SerialException: could not open port /dev/ttyACM0`**
STM32 没枚举出来，或者索引变了。看 §0「串口名也会变」：

```bash
ls -l /dev/serial/by-id/ 2>/dev/null || echo "没有任何串口设备"
```

有输出就换成那条 `by-id` 路径；空的是硬件/线的问题，不是软件。
**注意报的是 `could not open port` 而不是 `Permission denied` —— 前者是"设备不存在"，
后者才是权限（要加 `dialout` 组）。**

**4. `qt.qpa.xcb: could not connect to display` + abort**
SSH 下没加 `--headless`。

**5. 机器人不动 / 走走停停**
视觉频率掉了。看日志的 `fps=`：**低于 4 Hz 会被下游 watchdog 判死发零速**。
图卡检测器单帧 ~90ms，是巡线的 3~4 倍，所以它隔 3 帧才跑一次。如果 `fps` 很低，
先确认没有别的程序抢相机或 CPU。

**6. 转弯冲出去**
按 §3/§4 调。先看弯道里日志的 `wz`：
- **`wz` 上不去 0.4** → 降 `--steer-full-scale-cm`（9 → 7 → 6）。另一种可能是**没 pull
  新代码** —— 修单位前 `wz` 只有 0.03 rad/s，怎么调参数都没用。
- **`wz` 到 ±0.5 了还冲出去** → 不是增益问题，是策略执行不了这个转速，只能降 `--vx`
  （但这会让竞速分变少，先确认 `--vx 0.4` 时实际转弯半径是不是 0.8m）。

`--vx` 保持 0.4：弯中 3% 饱和只让机器人外偏 2.4cm，不是冲出去的原因。

**7. 想全部关掉**

```bash
# 顺序：先关策略（它占串口、退出时会关电机），再关视觉，最后连接器
pkill -f "humanoid_jetson_deploy/main.py"; sleep 1
pkill -f "run_policy_vision.py"
pkill -f "connector.py"
```

⚠️ **不要用 `kill -9`**——策略收不到 SIGTERM 就不会发 `send_disable`，**电机会保持使能**。

**8. `--wz-mode discrete` 打开了，脉冲也看到了，但机器人几乎不转**

先查 A（连接器）有没有 `--max-wz-accel 0`。默认 2.0 会把 0→0.4 拉成 0.2 秒的斜坡，
比这短的脉冲过完就剩个三角形，峰值也到不了 —— **B 的日志里 `wz=0.4` 是真的，
串口那头的波形是假的**。B 启动时会打一行提醒，漏了就看那一行。

## 9. 图卡通信

### 三个字段：观测和事件是分开的

| 字段 | 发多久 | 含义 |
|---|---|---|
| `qr` | **只有识别到的那一帧** | 当前识别结果，`-1` = 没看到 |
| `event_id` | **连续 5 秒**（`--card-hold-ms`）| 一次确认事件的唯一编号 |
| `event_action` | 连续 5 秒 | 那次事件的动作号 1-6 |

**`qr` 是一帧的脉冲，`event_id`/`event_action` 才是稳定信号。**

> ⚠️ **`qr` 只有一帧，别拿它当触发信号。** 它发给连接器，而连接器**只保留收到的最后一条**；
> 那一帧只有 20~70ms，理论上可能被错过。真正可靠的是 `event_id`——连续 5 秒都在，
> 接收端还按 ID 去重，所以同一张卡**不可能触发两次**（`shape_actions.py` 的
> `seen_event_ids`），这是结构上保证的，不靠调参。

编号来自 `shape_detector.py` 的 `action_map`，和 `connector.py:51` 的合法值域
是同一套（旧二维码时代留下的 1-6）。

### 谁执行哪个动作

| `qr` | 形状 | 动作 | **谁执行** |
|---|---|---|---|
| 1 | 圆形 | 举左手 | **STM32** |
| 2 | 五角星 | 举右手 | **STM32** |
| 3 | 正方形 | 抬左腿（右脚支撑）| **Jetson 单腿 ONNX** |
| 4 | 菱形 | 抬右腿（左脚支撑）| **Jetson 单腿 ONNX** |
| 5 | 十字形 | 举双手 | **STM32** |
| 6 | 三角形 | 左右摇头 | **STM32** |

**手臂和头不在那 12 个关节里**——它们挂在 STM32 上，走单独的串口消息：

| Type | 方向 | 载荷 | 含义 |
|---:|---|---|---|
| 3 | Jetson→STM32 | `<IB` `event_id, action_id` | 上半身请求，**只收 1/2/5/6** |
| 4 | STM32→Jetson | `<IBB` `event_id, action_id, status` | 1接受 2完成 3忙 4非法 5失败 |

Jetson 每 100 ms 重发一次直到确认；STM32 对重复 ID 只回状态、不重启动作。
腿指令的 watchdog 一旦超时，STM32 会中止进行中的上半身动作并回 status 5。

⚠️ **STM32 固件必须支持消息 3/4。** 没烧新固件的话 1/2/5/6 会被拒——
3/4（走 Jetson）和巡线不受影响。

### 链路

```
shape_detector.py → run_policy_vision.py → connector.py → UDP:5005 → main.py
  action 1-6          qr + event_id         原样透传     shape_actions.py
                      事件保 5 秒           不平滑       按 event_id 去重
```

- `connector.py` 明确注释 `qr` 是离散值、**不参与斜率限制**
- 视觉停发或超时，`connector.py` 把 `qr` 复位成 -1
- 掉一帧相机不会丢事件：保持窗口跨帧有效

### 停车期间按住直立：`hold_upright`（**已被 `card_tilt` 取代，默认关**）

> ⚠️ **2026-10-02：这条是早期的一个想法，正式方案是下面的 `card_tilt`（队友出的）。**
> `hold_upright` 默认**关**，要开得显式加 `--hold-upright`。
> **两条路动的是同一批关节，任何时刻只能开一条。**

**2026-10-01 加。** 视觉在 `processed < stop_until or processed < card_until`
（"为了让机器人站定读卡"的那整段）会在每个包里多带一个 `hold_upright: true`。
`main.py` 收到后**把腿部目标直接写成全零 12 关节，策略完全不参与** ——
和 `--fixed-policy examples/stand_upright_hold.json` 是同一个姿态（膝角 0，两腿全直）。

**为什么**：相机安装角 45° 是在机身直立时标定的。策略自己的"站住"姿态**向后仰约 20°**
（光轴变成 25°），而图卡的方形判据实测只在假设俯仰 **33~68°** 之内认得出 ——
后仰直接把卡框拒了；找不到框就退回 cy 兜底，而 cy 在 25° 下**会在 ~103cm 处就触发**
（本该 43cm）。按住直立之后光轴回到 45°，**一个图卡参数都不用为姿态重算**。

**时序**（`stopped` 是 `main.py` 现有的判据，卡动作也用它）：

```
走 ──► 视觉触发停车 ──► 策略自己站住（后仰 20°）──► 腿伸直到全零 ──► 读卡 ──► 交还策略
        vx=0 +                                 max|qd|≤0.2        光轴 45°      窗口关
        hold_upright=True                      才切过去，0.1s    认得出
```

| | |
|---|---|
| 什么时候切 | **等机器人真的停稳之后才切**（`main.py` 的 `stopped`：`max\|v\|≤0.02` 且 `max\|qd\|≤0.2`）。步态还在收尾时换姿态是没验过的，而且那一瞬策略的余动和新的静态目标会互相顶。代价是停车窗口前 0.2~0.4 秒还在用策略自己的姿态，3~5 秒的窗口随便吃 |
| **`stopped` 只管进入，不管维持** | 腿伸直的过程中 `qd` 会超过 0.2。每帧重判的话，保持会**在刚开始生效的那一刻被撤掉**，腿交回策略 → 静止 → 再保持 —— 两个姿态来回切。所以一旦进入，只有"视觉撤掉字段"或"抬腿动作接管"才结束 |
| 和动作的关系 | `decision.policy == "one-foot"`（卡 3/4 抬腿）**优先于**直立保持；卡 1/2/5/6 的动作由 STM32 直接做，腿可以一直是全零 |
| 命令会不会打架 | 保持期间 `step_policy.step()` **完全不被调用** —— 策略和全零目标是二选一，同一批关节任何时候只有一个来源。`connector` 斜降的 `vx` 此时也没有消费者 |
| 退出 | 窗口关掉就 `policy.reset()` 并交还策略 |
| 过渡 | `slew_limit` + `MAX_TARGET_DEVIATION_DEG` 限速，`Q_DEFAULT` 的膝角 0.30 → 0 约 5 帧 / 0.1s，不是瞬跳 |
| 字段缺省 | 老视觉不发这个字段，`main.py` 读成 false，行为和以前完全一样 |
| 需要 `--one-foot-model` 吗 | **不需要。** `snapshot` 现在只要 `--command-source vision` 就取，和图卡事件是两条独立的路径 |

### 停车重摆机身：`card_tilt`（**和 `hold_upright` 二选一**）

**2026-10-02 加。** 另一条解决后倾的路：**不由 Nano 摆姿态，由 STM32 摆。**
视觉在同一个停车窗口里多发一个 `card_tilt: true`，`main.py` 把它**两个边沿**变成
两条动作请求发给 STM32。STM32 把机身扳回安装姿态（相机就朝下 45° 了），并在整个
识别期间**上报加偏置之前的那份状态**。

**「冻结」= 保留加偏置之前的最后一个真值。** 偏置落地那一刻「站着后仰」这个事实
就不成立了（机身真的到 45° 了），所以只能在它还成立的时候记下来，之后一直报这个
值。模型以为自己还站着后仰，就不会去纠回来。

⚠️ **别把上报值和相机真实朝向"对上"。** 冻结值和机身实际姿态**不一致**，这是故意
的：固件骗的是模型，不是视觉。视觉的图卡几何必须用**静态安装角**，按停车窗口区分
（`run_policy_vision.py` 的 `effective_pitch`）。喂冻结值进去的话，43cm 处地面方框
判据只在假设俯角 [38.6, 59.0] 内认卡，冻结的 25° 直接被拒 —— 重摆就白做了。

> **这条是在用的那条。** 另一条 `hold_upright`（Nano 把腿写成全零）是早期想法，
> 已被取代、默认关。两条动的是同一批关节，**任何时刻只能开一条** ——
> 想退回 `hold_upright` 就加 `--hold-upright` 并把 `--card-tilt-ms` 设 0。

#### 固件那边是什么

固件是队友 `main` 上那套（`ACTION_ID_LEAN = 7` / `ACTION_ID_RESTORE = 8`；我们只
把号从 3/4 改成了 7/8，分支 `card-tilt-7-8`）。要点：

| | |
|---|---|
| 动作号 | 7 = 前倾、8 = 恢复。**必须是 7/8** —— 上位机 `protocol.py` 就是这两个号，对不上会落到 `Handle_Action_Request` 的 `default` 分支回 `INVALID` |
| 加在哪 | **只有左右 leg pitch 两个关节**（协议 0/6 = `l_leg_pitch` / `r_leg_pitch`）。`lean_applied` 全文件只加到这一处，别的关节一个不加 |
| 多大 / 多快 | 20°（`0.3491 rad`），0.6 rad/s 的**斜坡**爬过去 = **0.582 s** |
| 怎么进 | 收到 7 就 `CaptureFrozenState()`（抓快照）+ 让偏置爬上去。两个都**不占 `robot_state`**，所以前倾能跨着后面的手臂动作持续 |
| 怎么出 | 收到 8 **同一瞬间**解冻，同时起 0.582 s 的回斜坡 |

⚠️ **固件不判断"该不该锁"** —— 收到 7 就锁、就爬。时机全在上位机这边：

#### 上位机这边要守住的两件事

**① 7 要等机器人站定再发。** 固件是**收到 7 的那一刻**抓快照、也是那一刻起斜坡的。
停车触发帧上机器人还在刹车，抓下来的是个走路中间的姿势 —— 2026-10-02 实机就是
这样：机身 **-2.85°（水平）**、一条腿直一条腿弯 27°。+20° 于是不是"把后仰扳回来"，
而是**在水平上再往前推 20°**；模型解除冻结时看到一个从没命令过的姿态，甩出了
**左髋 87° 的大跨步**。

`main.py` 里发 7 的条件因此是 `card_tilt and stopped`（`stopped` = 速度指令为 0
且 `max|qd| ≤ 0.2`）。等不到就**不发** —— 窗口关了 `card_tilt` 变假，什么都不会
发出去。

**② 发完 8 之后策略要继续看旧状态 0.65 s。** 固件是同一瞬间解冻的，可机身还要
0.582 s 才爬回站姿；这期间喂真值，模型看到的就是那个倾斜。`main.py` 在发 8 那一刻
存一份快照，`CARD_UNTILT_HOLD_S = 0.65` 之内继续喂它，过去了才交回真值。

⚠️ 固件那两个常数（20° / 0.6 rad/s）上位机是**照着算的**。固件改斜坡，这里的
0.65 s 要跟着改。

时序：

```
走 ─► 触发停车 ─► [刹车 + 站定] ─► [锁 + 前倾 0.58s] ─► 识别 ─► [8 + 保持 0.65s] ─► 动作
       card_tilt=True   ↑ main.py 等到 stopped 才发 7              card_tilt=False
       （7 还没发）                                                 → action 8
       ↑                                                            ↑ 策略继续看旧状态
       这整段不跑分类器，见 --card-tilt-ms
```

**`--card-tilt-ms`（默认 1000 → 1300 → 2026-10-02 改成 1800）**：停车后的这一段
**完全不跑图卡检测**（`tilting` 门）。它要装下「等站定 ~0.9s + 前倾 0.58s ≈ 1.5s」
再留点余量。**太短就会在机身还在倾斜时开始认卡**，而几何按安装姿态算 —— 每一张
都会被 `ground` 拒掉（实机就是 `rej=ground:197`）。

实车看 `[vision]` 那行 `(body …)` 什么时候冻住能确认锁存点。改完确认
`--card-stop-ms`（默认 3000）还留得下识别时间：`1800 + 识别 ≈ 2200`，够。

⚠️ **8 必须排在形状动作（1-6）前面**（`main.py` 里 card_tilt 那段在形状段上面）。
7/8 不占 `robot_state`，所以 8 不会被 BUSY 挡住；但如果 8 在手臂动作**中途**到达，
它会把 `active_event_id` 覆盖掉，手臂动作的 DONE 就永远发不出来，上位机会一直等。
顺序不能动。

### 起跑门控：扫到二维码 + 认出第一张图卡才起步

赛场上三个终端开机就跑，但车不能一启动就走。`--start-gate` 让 B 把 `vx/wz`
按在 0，直到**两个阀**都通过：

| | 条件 | 现场怎么给 |
|---|---|---|
| **阀1** | 解出一个二维码，payload 等于 `--start-gate-qr-payload`（默认 `"1"`，2025 规则那个码） | 队友把码**举在机器人前方 30~40cm**，稳一下 |
| **阀2** | 第一张图卡**分类成功**（认得出是圆形/五角星/… 不是"看到有卡"），连续 `--start-gate-shape-frames` 帧同名 | 起点那张卡自己就在画面里（40cm 以内） |

```bash
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless \
    --start-gate both --start-gate-qr-payload 1 --qr-every 5
```

两个都是**只锁存、只升不降**：过了就是过了，之后整趟不再看二维码、不再判门控。
释放之后走的是原来那套"走到画面固定位置 → 停车 → 重摆 → 投票 → 出 event"，
**停车判据一个字没动**（`run_policy_vision.py` 里那段 `card_armed` 判据）。

#### 为什么门控期间要把机身按住直立

策略自己的站姿**向后仰约 20°**，而相机 45° 是在直立时标定的，分类前的几何闸
只认假定俯角 **38.6°~59.0°**。后仰时每一张卡都会被 `rej=ground` 拒掉 →
阀2 永远不过 → **机器人永远不走**（而且要吃到"发令后 10 秒未启动"的判负）。

所以门控期间 B 会发 `hold_upright=True`（`main.py:492` 那条已有的路，全零关节
目标 = 腿伸直 = 安装姿态），C 那边把它扳直。这条链路 A、C **零改动**。
释放那帧仍然按着，下一帧才落，`card_tilt` 不会和它撞在同一帧。

#### 三个会踩的坑

1. **起点那张卡本来就在停车线以内**（`--card-trigger-dist-cm` 43，卡在 40cm 内），
   而 `card_armed` 初值是 `True` —— 不按住的话，**机器人还没起步就会停车、重摆、
   出 event**。门控期间把它按成 `False`，只在释放那一帧置回 `True`。
2. **释放后可能立刻进停车读卡，一步都不走** —— 卡在线内，这是那条判据的忠实行为。
   释放横幅会打印实测框宽，看到就知道：

   ```
   [start-gate] 起步：第一张卡实测框宽 210px / 停车线 99px —— 已经在线内，会立刻进停车读卡
   ```

   想让它先走一段：把车往后退（改起点），或者调小 `--card-trigger-dist-cm`
   —— 后者是**全局的**，会影响另外两张卡，改完要回归整趟。
3. **门控期间不调用 `controller.command()`** —— 站着等十分钟，PID 的积分会拿一段
   看不见的误差把自己喂饱，起步第一帧就用它去转。和停车窗口同一个处理。

#### 现场看什么

门控还关着时每 `--start-gate-log-s` 一条：

```

### 两段式：先认出"有"，停稳了再认"是哪个"

**走路时的抖动会把卡片外框打成 2~3 条断线，四边凑不齐，整个找框通道返回空。**
所以分成两段，因为这两件事难度差一个量级：

| | 什么时候 | 靠什么 | 要求 |
|---|---|---|---|
| **① 有图卡** | 行走中 | `dbg["presence"]`：**一圈细暗边框围出一块亮纸面**（卡片 = 暗边框 + 白纸；巡线被打成实心粗笔，没有亮孔）。时间累积：最近 9 次里 ≥3 次命中，且最近 3 次内必须有 | 只要能认"有"，**只负责减速**，不判是哪个 |
| **② 够近了** | 行走中 | **有真框**：量化 `dbg["quad_work"]` 的宽，够 `--card-trigger-dist-cm` 换算出的 px 就触发。<br>**没有框**：退回 `dbg["presence_cy_frac"]` 的 cy | 框宽对机身俯仰不敏感，cy 敏感 —— 见 §5 停车距离 |
| **③ 是哪个** | **停下来之后** | 找框 + 分类。看见卡之后检测就升到 `--card-every-stopped`，停稳后相机不动，认得更稳 | 5 秒窗口内认出来 |

### 找框管线（2026-09-27 重构，`c888c2c`）

**两条平行的二值图**，这是理解整条管线的关键：

| 二值图 | 怎么来 | 给谁用 |
|---|---|---|
| `_binary_selective` | blackhat核9 + 自适应阈值 + 形态学 + **笔画宽 [1.5,7] + 细长度过滤** | Hough / LSD / corner / CC 四条通道 |
| `_card_ink` | **原始灰度直接 Otsu**，不做任何线宽筛选 | ring 通道 |

**为什么要有第二条**：`_binary_selective` 是为**压 2cm 巡线**调的，代价是把
**0.5cm 的卡框锯出锯齿**。实测 6card 31 张里，只有 10 张的卡框轮廓在
`approxPolyDP(eps=0.02)` 下还能收成 4 个顶点 —— **而那 10 张恰好就是老管线能过的全部**。

**候选通道现状**（实测每帧）：

| 通道 | 出多少 | 评价 |
|---|---|---|
| `_hough_quads` / `_lsd_quads` | 各 256（硬上限） | **对卡全被 `area_max` 杀**，等于废的；只贡献被拒的量 |
| `_corner_quads` | 0~27 | **主力**，6card 上约 2/3 的赢家来自它 |
| `_cc_quads` | 1~2 | 用 `minAreaRect`（旋转外接矩形）拟合透视下的梯形，对近卡系统性偏大 |
| `_ring_quads(ink)` | 0~2 | **新增，约 1/3 的赢家**。见下 |

**ring 通道的选择性来源是"有孔"**：卡框是个闭合细环；巡线/道线是**开放曲线，
没有孔**；卡内的图形（星/圆/方）是实心块也没有孔。再叠 `_drop_nested`
（一张卡上有外框 + 内部图形两圈环，丢掉落在别人框里的）。

**ring 候选跳过 `_refine_quad` 和 `_verify_quad`** —— 它的框就是那条环轮廓本身。
实测这两步会把好框拒掉（五3 四边命中 `[0.53 1.00 0.47 1.00]`、正5 `[1.00 0.93 1.00 0.47]`，
两条边过不了 0.65 的底线，而这两张卡单独 warp 出来判得完全正确）。
**代价是失去了闭合度那道假阳性防线**，见 §8 的假阳性条目。

⚠️ **②段必须是真框，不能用 `presence`。** 2026-09-26 实车日志：

```
[shape] found=0 presence=1 ... quad=512g0v0 top=- cy=0.74 cue=0.25 armed=1
[shape] card 121px of 118px (cy=0.88) -> stand still 3000 ms
   ↑ 框宽到了就停，cy 只作参考 —— 上面这行 cy=0.88 按配置几何是 13cm，实际 27cm
```

**一个框都没找到（512 个候选全被几何闸门拒掉），`cue` 只有 0.25。**

⚠️ **这一段以前写的是"现在触发要求 `card_found`" —— 那是错的，代码从来没这么做过。**
实际的判据是：

```
有真框（quad_work 存在） → 量框宽，够 --card-trigger-dist-cm 换算出的 px 就停
没有框                    → 退回 presence_cy_frac（那时它来自 cue 框的质心）
```

**没框那条路是刻意留的**：走路抖动会把卡框打碎，整段行程一个框都收不拢，
只认框就永远不停。代价是 cue 框的质心**跟卡片有多近没有严格关系**，
所以那种情况下停在哪比较看运气。`test_a_strong_presence_cue_stops_it_even_with_no_box`
钉着这个行为。

**但实跑里"没框"是常态**：2026-10-01 两次跑，停车那一刻都是 `found=0 quad=2g0v0`。
也就是说**框宽那条路根本没接上，停的还是 cue 的 cy** —— 而 cy 对机身俯仰极敏感
（见 §5）。**真正的瓶颈是走路时收不出卡框，不是判据选哪个量。**

```
巡线 → 看到图卡（打 flag）→ 减速继续走（不停）
                            ↓  框宽够 --card-trigger-dist-cm（默认 43cm → 99px）；
                               没框时退回 cy 够 0.400
                          停车（每帧分类）
                            ├─ 认出 → qr=N → 保持 5 秒 → 恢复巡线
                            └─ 3 秒没认出 → 不减速，照 --vx 走

每张卡只触发一次：flag 要连续 4 次检测都看不到卡才清除。
```

> **2026-09-26 实车：还漏了第二次触发，已补。**
> 触发过一次的卡，会在车开过去之后**再触发一次停车**。日志：
>
> ```
> [shape] box centroid at 0.84 -> stand still 3000 ms   ← 卡片在画面最底部

>

> 真正的新卡是从远处（`cy≈0.30`）进来的，第一次靠近时就能拿到。

>
> **2026-10-02 又漏了一次，同一个根因的另一个洞。** 那次车停在五角星前面
> （不是开过去），`card_armed` 那套没兜住，因为卡根本没离开过画面。真正的漏子是
> **`presence` 被 `armed` 门控**：检测器内部那套动作闸（调用方早就不用了）在停车
> 窗口里自己开了一次火 → `armed=0` → `dbg["presence"]` 恒假 → 调用方数满 4 次
> "漏检"，把 `card_flag` / `card_triggered` / **投出来的票** 一起复位。后果是
> **两个**：
>
> - 那次停车 5 张 pentagon 的票全被抹掉，出票分支拿到空字典静默返回 ——
>   车停了三秒、扳直、恢复，**什么都没做**；
> - `card_triggered` 跟着复位 → 5 秒后**同一张卡又触发了一次停车**。
>

> 差 **0.05 秒**没躲过去。**补法**：`dbg["presence"]` 去掉 `armed` 门控
> （`shape_detector.py`，两处）。`presence` 说的是"画面里有一张卡"，是图像事实，
> 和"这张卡我还要不要开火"无关。"每张卡只触发一次"改由 `card_triggered` 保证，
> 它只在**卡真的离开画面**之后才复位。
> 回归测试：`test_presence_survives_the_detector_disarming_itself`。

**3 秒没认出来之后是"慢慢挪"，不是"全速冲"**。以前那一段走的是 `vx=+0.400`

不是异常。实测 6card 上赢家约 1/3 来自 ring、2/3 来自 corner 通道。

### ⚠️ 卡片会挡住巡线的近带（停车位置换来的新问题）

当时 `--card-trigger-frac 0.5`（≈32.5cm）让车停在离卡 **22~34cm** 的地方。而**巡线的近带覆盖 z ≈ 20~27cm**——
**卡片正好落在里面**。近带看到的是卡片的黑边框，不是赛道线，于是 `err`/`conf` 全乱：

```
停车识别完，恢复行走那一刻：
  conf 0.96~0.99  →  0.00 ~ 0.46      ← 检测崩了
  wz               →  +0.5 / -0.5 来回撞   ← 拿垃圾帧在转向
```

**旧阈值 0.75 反而没有这个问题**——那时车停在 10cm 内，卡片掉在画面下边缘之外，
根本不在近带里。所以这是 0.5 换来的，不是原来就有。

**解法（2026-09-26 定稿）：停车窗口一结束，立刻恢复巡线。没有盲走这一段。**

`--card-clear-s` / `--card-clear-conf` 已经删掉了，对应两代方案都被实车否掉：

| 方案 | 怎么做的 | 为什么否掉 |
|---|---|---|
| 直行开过去（`2aef636`） | `wz=0` 开 2 秒 | 弯道上白白往外偏，且检测没恢复就交还 |
| 回放停车前指令（`ed31661`） | 发停车前 1 秒的平均 `wz` | 抄的是**转向率**不是**曲率**，`vx` 砍半后**每米转角翻倍**，转过头 |
| **都不做（现在）** | 窗口一关就交还控制权 | — |

**并且停车期间不再喂控制器。** 这是这次真正的修法：

```python
if processed < stop_until or processed < card_until:
    vx, wz = 0.0, 0.0
    controller.reset()          # 空闲 + 复位
else:
    vx, wz = controller.command(debug, confidence, previous_dt)
```

以前是**每帧都调 `controller.command()`，然后再把 `vx/wz` 覆盖成 0**——
于是停车那 8 秒里，被卡片污染的 `err` 一路灌进 PID 的**积分项**和
**滤波后的微分项**（`filtered_derivative` 的 `err_window`/`last_median`/`derivative`）。
窗口一关，这三样带着 8 秒的垃圾一起进第一帧真数据 —— 车**不是从弯道上的平衡点继续**，
而是从一个被卡片推歪的点重新起步。**"过完卡片往反方向拐"就是这么来的。**

弯道上的稳态是 P（近带误差）+ 前瞻（远带）+ bias 三者顶出来的一个平衡点
（`--bias-cm` **默认 0**，开了才算一项）。
停车期间一直在喂它错数据，等于把这个平衡点搬走了。

**回归测试锁住了这一点**：`test_speed_resumes_only_after_the_hold_window` 断言
窗口关闭后第一帧的输出**必须等于一个全新控制器对同一帧的输出**（`assertAlmostEqual`），
任何残留状态都会被抓住。

### 停车再启动，究竟破坏了什么（2026-09-26 全链路审计）

| 层 | 停了会怎样 | 0.5 秒级 / 步态周期级 | 切片能救吗 |

#### ⭐⭐ 巡线检测器自己的状态（2026-09-26 补，之前漏了）

`line_detector_v1_warp.py:224` 有一份 18 项跨帧状态，**"停→启"那一轮我完全没查它**
（当时只查了运动侧那条链）。其中两条是**自我强化**的：

| 状态 | 为什么致命 |
|---|---|
| **`last_lane_center_x`** | **直接当下一帧的扫描提示**（`:1058`）。锁到错的位置 → 下一帧从错的位置开始找 → **自己把自己拽住，回不来** |
| **`smoothed_err`** | 融合误差的 EMA，α=0.88，**长记忆** |
| `last_base_err` / `last_angle_err` / `last_far_dist` | 丢线时**原样重发**（`:1449-1452`）|
| `last_lane_width_px` / `last_band_mask` | 下一帧的提示 |
| `near_err_history` / `shake_active_frames` / `diff_rms_px` | 抖动检测 |
| `startup_frames` / `last_bottom_lock_valid` / 红条计数 | 其余 |

**实车签名**（丢线时）：`conf` 掉到 0.2~0.5、**`lock=0pair=0.00`**、`ang` 在 ±70 之间翻、
`far` 在 +104/−61 之间翻，而且**十几秒不恢复**。

**修法**：加了 `LineDetector.reset_state()`，在**停车窗口关闭那一刻**和控制器一起清成全新状态。
**依据是用户的原话**：同一个弯道，**进程全新启动就没问题** —— 那就是"状态是全新的"。

> ⚠️ **证据还不完全一致**：早先那次 Ctrl+C 掉 B 再重启（也是全新状态）**仍然是坏的**。
> 所以这一条**要实测**：如果 `reset_state()` 之后丢线还是回不来，那说明不是状态的事，
> 得从画面本身找原因（加 `--dump-on-loss` 存帧）。

#### ⭐ `hold` 泄漏（已修）

`reset()` 故意不清 `hold`（为了丢线耐心），而停车期间 `command()` 根本不跑，
所以 **`hold` 里一直留着停车前的 `(vx, wz)`，可能是 (0.4, 0.5)**。交接后头几帧若是无效帧
（卡片还在挡 → `conf=0` 或 `lost>0`），`policy_bridge.py` 会把**这条停车前的指令原样重发**，
最长 `--lost-hold-s`=0.2 秒——**这就是已经被否掉的"回放"换个形式回来了**。

现在停车分支传 `controller.reset(clear_hold=True)`，**恢复走的那一刻**（`stop→walk` 的下降沿）
B 会打一行：

```
[vision] card window closed; cold start (hold=+0.00,+0.00 lost_s=0.00)
```

**看到 `hold` 非零就是没清干净。**

⚠️ **这一行的时机是"停→走"，不是"刚停下"，而且必须在本帧 `detector.process()` 之前。**
第一版把它放在 `process()` 之后，于是**恢复走的第一帧仍然是用脏状态算的**，只清到了第二帧——
而决定往哪走的就是第一帧。同时帧时间戳必须在 `cap.read()` **之后**取（`stop_until`/`card_until`
都是用它设的），否则窗口判断天然慢一帧。两条都有测试钉住：
`test_the_handover_resets_the_detector_before_the_walking_frame`。

#### 步长是一个数（2026-10-03 定），不再跟速度走

> **⚠️ 分线说明：这一节只对 `policy49`（49 维）成立。**
> 新线 `vision6card`（47 维）上观测里**没有** `[步距, 交叉]` 这两维，
> 所以这一整块在新线上不存在 —— 新线可以跳过本节。

**现在只有两个数：速度 0.2 m/s，步长 5 cm。** 两个都在 `config.py`：

```python
MAX_COMMAND_VX  = 0.2   # m/s，视觉有有效检测时发的前进速度
STEP_LENGTH_CM  = 5.0   # cm，喂给策略的步幅观测值
```

`main.py` 的 `--step-cm` 默认就是这个 5.0，**写多少就是多少，不随 `vx` 变**。
四种命令源（vision / fixed / curve / scripted）横幅打的是同一行：

```
Step: 5.00 cm (--step-cm), independent of vx; the cadence is the policy's own
```

**唯一的例外：`vx = 0`（停下）时步长发 0，不是 5cm。** 恒定发 5cm 会让策略在
停车时迈原地步（真漂移），而且 `qd>0.2` 会让 `main.py` 的 `stopped` 判据失效、
`ShapeActionController.wait_stop` 4 秒后抛 TimeoutError。
`policy_runner.py` 里那一行 `if velocity_command[0] > 0.0 else 0.0` 就是这个边界。

**为什么不再用比例。** 以前步长是"每 m/s 给多大步距"（`--max-vx` / `--max-step-cm`
定出系数，实际步距 = `vx × 系数`）。两个毛病：

1. **改速度会顺手改步长。** 2026-10-03 把速度默认从 0.3 改成 0.2，系数跟着从
   0.2667 变成 0.200 —— 连**不写那两个参数的**命令（`--command-source fixed
   --vx 0.2`，正是用来判断姿势的那条）步长都从 5.33cm 掉到 4.00cm。
2. **同一个 `vx` 下，写不写那两个参数给出不同步长**（0.200 vs 0.2667 → 4.00 vs
   5.33cm），而横幅上完全看不出来。

现在这两个参数**已经删除**（`--max-vx` / `--max-step-cm` / `config.STEP_DISTANCE_PER_MPS`
都没了），只有 `--step-cm` 一个入口。

⚠️ **步长≠结果速度。** 步频是策略自己的，会跟着 `vx` 和步长变（实测：`vx` 从
0.3 降到 0.2 反而步频变快）。所以 5cm 是"要求策略走的步幅"，实际走多快要看车。

停→走边界上**没有缓冲段**：`--card-slow-vx` / `--card-resume-ms` 都已删除，
释放的那一帧就是全速（只剩连接器 `--max-vx-accel` 的斜坡）。

#### 怎么量

**为什么光看日志不够**：视觉日志是 **2Hz 抽帧**的（每 0.5 秒一行），而重启后
`vx` 从 0 爬到 0.4 只要 **0.4 秒**——**这一整段在日志里只占半行，根本看不见**。
`main.py` 的 `|obs|max` 又只有一个标量，看不出 47 维里是哪一维在跳。
所以要在 50Hz 上同时看到三件事：**发出去什么 → 策略收到什么 → 车实际做了什么**。

| 工具 | 看哪一段 | 频率 |
|---|---|---|
| `connector.py --tap-port` | **发出去的指令**（原样镜像）| 50Hz |
| `--tap-port` 的监听端 `new_vision/scripts/tap_listen.py` | 落成 CSV，带本机到达时间 | 50Hz |
| `POLICY_OBS_CSV` | **策略收到的 47 维观测**，按名字 | 50Hz |
| `records/motor_positions/*.csv`| **车实际做了什么**（电机目标/实测/IMU `rpy`）| — |

```bash
# 终端 A：连接器把每一包镜像到 5010
python -u connector.py --vision-port 5006 --policy-port 5005 --tap-port 5010 \
  --max-vx-accel 1.0 --max-wz-accel 2.0

# 终端 A2：监听端（跟 connector 同一台机器 → 同一个时钟）
python -u new_vision/scripts/tap_listen.py --port 5010 --out logs/tap.csv

# 终端 C：把 47 维观测按名字录成 CSV
POLICY_OBS_CSV=logs/obs_$(date +%H%M%S).csv \
python -u humanoid_jetson_deploy/main.py --policy walking \
  --model humanoid_jetson_deploy/policy.onnx \
  --port /dev/ttyACM0 --command-source vision --udp-command-port 5005 \
  --enable-motors --no-plot --max-seconds 60
```

`POLICY_OBS_CSV` 不设就完全不产生文件，平时跑没有开销。
tap 实测 50Hz 下 **100/100 不丢包**（UDP，但同机回环足够稳）。

**判读的核心一条**：重启后 1 秒和 3 秒内，

```
实测 yaw 率（motor CSV 的 rpy[2] 差分）的符号   vs   tap.csv 里 wz 的符号
```

- **一致** → 视觉确实发了那个方向，车也照做了 → **是视觉读数的问题**
- **不一致** → 视觉发了左、车往右 → **是策略/步态的问题**

**这一条是整件事到现在唯一没做过、且能一刀切开的测量**，它决定后面往哪修。

### 代价（实机实测，Orin @1280×720）

| 画面 | 巡线 | 图卡检测 | 只用巡线 | 每 6 帧 |
|---|---|---|---|---|
| 无图卡 | 28.9 ms | 31.9 ms | 35 Hz | **29 Hz** |
| 有图卡 | 28.4 ms | 94.5 ms | 35 Hz | **23 Hz** |

**停车时曾经是"每帧都跑"**（`--shape-every` 的节流被停车窗口取消），于是
`28.4 + 94.5 ≈ 123 ms` → 循环只有 **6~8Hz**。这不只是慢，**是控制质量**：

```
视觉每帧发一包 → connector.py 50Hz 零阶保持 + 斜率限制
                → policy_runner.py 50Hz → ONNX → 关节目标
```

策略**没有"一步一决策"那一层**，它每个 50Hz tick 观测当时的 `wz` 连续输出关节目标。
所以一份被保持的包会被喂几拍：

| | 视觉帧率 | 一份包被喂几拍 |
|---|---|---|
| 行走 | 16~20Hz | **≈3 拍** |
| 停车（改前）| 6~8Hz | **≈6~8 拍** ← 转向是一块一块的 |
| 停车（改后）| ~12Hz | ≈4 拍 |

`--card-every-stopped 2` 把停车期间的图卡检测改成每 2 帧一次，循环回到 **~12Hz**，
分类尝试次数从 ~7.7 次/秒到 ~6.2 次/秒（够用：实车 `qr` 在 5 次调用内就出来了）。
| 有图卡+干扰 | 34.1 ms | 122.5 ms | 29 Hz | **18 Hz** |

**图卡检测比巡线贵 3~4 倍。** 贵的部分只在图卡真进视野时发生，所以平时只掉 15%，
图卡进视野那两秒掉到 23 Hz。**循线变差就先加 `--no-shape-detect` 排查。**

## 10. 相位时钟跨棍（独立运行）

这是 `humanoid_jetson_deploy/phase_clock_main.py` 的独立入口，不属于上面的“三个终端”视觉巡线链路。
它直接打开 STM32 串口并以 50Hz 控制电机，因此**不要同时运行 `main.py`、`connector.py` 所连接的策略进程，或其他占用同一 STM32 串口的程序**。

先按 §0 确认串口路径。下面用 `/dev/ttyACM0` 举例；如果机器提供了稳定的 `/dev/serial/by-id/...`，应替换成那条完整路径。

### 终端 A：启动相位时钟

```bash
cd ~/jetson_orin_code
source .venv/bin/activate

# 先干跑：连接 STM32、记录数据，但不使能电机
python -u humanoid_jetson_deploy/phase_clock_main.py --port /dev/ttyACM0
```

确认配置中的电机与 IMU 标定均已确认，并且有可靠的外部支撑后，实车运行命令为：

```bash
python -u humanoid_jetson_deploy/phase_clock_main.py --port /dev/ttyACM0 --enable-motors
```

启动后终端会显示 `Waiting for UDP {"start": true}`。程序先检查 STM32 状态、IMU 和编码器数据；在收到启动信号时，还会检查关节角是否在 `Q_DEFAULT` 的 ±10° 内、关节速度是否不超过 0.2 rad/s。未通过时信号会被忽略，摆好初始姿态、等机器人静止后再发送一次。

### 摆好起始位置后：终端 B 发送一次启动信号

按该实验的起始布置恢复蹲姿，并让前导脚脚尖距棍子近边 8cm。保持终端 A 运行，在另一个本机终端执行：

```bash
cd ~/jetson_orin_code
source ../.venv/bin/activate
python -u humanoid_jetson_deploy/tools/send_phase_start.py
```

发送器默认只向本机 `127.0.0.1:5008` 发送一次 `{"start": true}`。要改端口时，主程序和发送器需同时设置同一个端口，例如主程序加 `--start-port 5018`，发送器加 `--port 5018`。启动信号不是远程网络接口。

这是一段一次性固定相位序列：程序报告 `sequence_finished` 后会发送电机失能命令并退出；按 Ctrl+C 中断也会走失能清理。**失能只表示停止发送使能命令，不代表机器人已经成功跨棍或能自行站稳**，结束后的扶持/站立接管由现场人员负责。

默认日志写入 `humanoid_jetson_deploy/logs/phase_clock_run.csv`，可用 `--log <路径>` 修改。常用可选参数：

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `--port` | `/dev/ttyACM0` | STM32 串口；按 §0 替换为实际设备 |
| `--baud` | `921600` | 串口波特率 |
| `--enable-motors` | 关闭 | 使能电机；干跑时不要加 |
| `--start-bind` | `127.0.0.1` | 启动信号监听地址，必须是本机 IPv4 loopback |
| `--start-port` | `5008` | 本机 UDP 单次启动端口 |
| `--bundle` | 内置 phase-clock 模型目录 | 更换模型包目录 |
| `--log` | `logs/phase_clock_run.csv` | 运行数据 CSV 路径 |

日志包含 STM32 状态时间戳/序号、控制相位与 tick、关节角和速度、IMU 数据及模型动作；它用于复盘，不是跨棍成功判定。实车行为和跨棍成功率仍需现场试跑确认。
