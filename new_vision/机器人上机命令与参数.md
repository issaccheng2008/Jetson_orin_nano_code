# 机器人上机命令与参数

> 视觉侧跑在 Nano 板的 `jetson_orin_code` 仓库（`new_vision/`）里，通过 UDP 把
> `{vx, wz}` 发给走路策略。本文是**照着敲就能跑**的操作手册。
>
> 数据来源：链路与参数从代码实测（2026-09-24）；赛道几何由 1:1 渲染图与 DXF 圆弧互证。


## 1. 三个终端

**A — 连接器**（视觉 → 策略的中转，50Hz 零阶保持 + **斜率限制**）

```bash
python -u connector.py --vision-port 5006 --policy-port 5005 \
  --max-vx-accel 1.0 --max-wz-accel 2.0
```

`vx` 和 `wz` 都按这两个加速度上限逐拍逼近目标，**不再有阶跃**（0.4 m/s 用 0.40s、
0.5 rad/s 用 0.25s）。不写这两个参数也是同样的默认值。想对比关掉的效果就传 `1e6`。

**B — 视觉**（相机 → 巡线检测 → PID → UDP）

```bash
python -u new_vision/jetson/run_policy_vision.py --camera 0 --headless
```

**其他全是默认值，不用写。** 当前锁定：`--vx 0.4 --max-wz 0.5 --steer-full-scale-cm 10
--preview-gain 0 --bias-cm 5 --bias-gate-px 12 --lost-hold-s 0.2 --deriv-pole 0.78`。

⚠️ `--camera` 索引会变（§0），每次先按 §0 探测。

> 2026-09-25 实车锁定：`--preview-gain 0` + `--bias-cm 5`，跑得很好。原因见 §3。

**C — 走路策略**（收 UDP → ONNX → 串口 → 电机）

```bash
# 先干跑（不使能电机），确认方向
python -u humanoid_jetson_deploy/main.py --policy walking \
  --model humanoid_jetson_deploy/policy.onnx \
  --one-foot-model humanoid_jetson_deploy/policy-one-foot-standing.onnx \
  --port /dev/ttyACM0 --command-source vision --udp-command-port 5005 \
  --no-plot --max-seconds 30
```

```bash
python -u humanoid_jetson_deploy/main.py --policy walking \
  --model humanoid_jetson_deploy/policy.onnx \
  --one-foot-model humanoid_jetson_deploy/policy-one-foot-standing.onnx \
  --port /dev/ttyACM0 --command-source vision --udp-command-port 5005 \
  --enable-motors --no-plot --max-seconds 10
```

方向对了就把末尾换成 `--enable-motors --no-plot --max-seconds 10`，其余一字不动。

⚠️ **`--one-foot-model` 是图卡 3/4 号（抬腿）用的**，不给它的话那两个动作做不了，
巡线和另外四个动作不受影响。

⚠️ **两个模型路径别搞混**：

```
humanoid_jetson_deploy/policy.onnx                    49 输入  ← 走路（--model）
humanoid_jetson_deploy/policy-one-foot-standing.onnx  46 输入  ← 单腿（--one-foot-model）
humanoid_jetson_deploy/models/*.onnx                  47 / 48 输入，会被拒
```

`config.OBS_DIM = 49`，我们扫过仓库里全部 12 个 onnx，只有 `policy.onnx` 是 49 输入。
注意 `humanoid_jetson_deploy/models/policy.onnx` 和 `humanoid_jetson_deploy/policy.onnx`
**是两个不同的文件**（同尺寸不同内容），别搞混。

**SSH 下必须加 `--headless`（视觉）和 `--no-plot`（策略）**，否则 `cv2.imshow` 会 abort。

三个终端用 tmux：

```bash
tmux new -s robot      # Ctrl+b c 开新窗口，Ctrl+b 0/1/2 切换，Ctrl+b d 脱离
tmux attach -t robot   # 重连
```

**掉线不等于进程死**——tmux 里进程会继续跑，机器人继续走。**永远带 `--max-seconds`。**

### 图卡测试

**A 和 C 不变**（C 记得带 `--one-foot-model`，不然 3/4 号卡的抬腿做不了）。

**B 要调 `--shape-every 2`** —— 检测的时间窗数的是"检测调用次数"不是视频帧，
默认 6 时 9 次的窗口跨约 1.8 秒，太慢。

```bash
cd ~/jetson_orin_code && source .venv/bin/activate
python -u new_vision/jetson/run_policy_vision.py --camera 0 --shape-every 2 --headless
```

**车走近图卡时应该依次发生：**

| 顺序 | 车 | B 的日志 | C 的日志 |
|---|---|---|---|
| 1 | **减速**（0.4 → 0.2），但继续走 | — | — |
| 2 | 停住 | `[shape] box centroid at 0.7x -> stand still 3000 ms` | — |
| 3 | 站着不动 | `[shape] qr=3 (square) held 5000 ms` | 收到 `event_id`，开始动作 |
| 4 | **做动作** | — | 1/2/5/6 走 STM32；3/4 走单腿 ONNX |
| 5 | 5 秒后恢复巡线 | `qr` 回 `-1` | 恢复正常走 |

**关键：`stand still` 只该出现一次。** 同一张卡不会触发第二次（接收端按 `event_id` 去重）。

**出问题看这张表：**

| 现象 | 多半是 | 怎么办 |
|---|---|---|
| 走到图卡跟前不停 | 质心没压到阈值 / 存在信号没触发 | 先看 `--shape-every` 是不是给大了；卡太偏、车太快也会漏 |
| 没卡也减速/停 | 误报 | 把日志和当时画面给我，看 `presence_box` 框住了什么 |
| 停了但一直 `qr=-1` | 停稳了也分类不出 | **那是已调好的那条路，别乱调**，把画面给我 |
| 停 3 秒自己走了、没发 `qr` | 分类没在窗口内定下来 | `--card-stop-ms` 加大（3000 → 5000）|
| 上半身动作不做 | **STM32 固件没烧新版本** | 见 §9，1/2/5/6 需要固件支持消息类型 3/4 |
| 1/2/5/6 做了、3/4 不做 | C 少了 `--one-foot-model` | 补上它 |
| 想完全关掉图卡 | — | B 加 `--no-shape-detect`，`qr` 恒 -1 |

⚠️ **`--card-hold-ms`（默认 5000）是规则要求的动作窗口，先别动。**
`--card-stop-ms`（默认 3000）只是"等分类"的上限，调它是安全的。
`--shape-lift-seconds`（默认 4）是单腿抬起的时长，规则要求 ≥3 秒。

### 只测转弯步态：一个终端就够

`--command-source fixed` 恒定发一组 `vx/wz`，**直接绕过视觉、连接器和 UDP**——
不需要 A 和 B，也没有 watchdog。用来单独看步态在转弯时垮不垮。

```bash
# 先干跑（不使能电机），确认方向和步态
python -u humanoid_jetson_deploy/main.py --policy walking \
  --model humanoid_jetson_deploy/policy.onnx \
  --port /dev/ttyACM0 --baud 921600 \
  --command-source fixed \
  --vx 0.4 --wz 0.5 --walk-seconds 8 \
  --no-plot --max-seconds 20

# 方向对了再上电机
python -u humanoid_jetson_deploy/main.py --policy walking \
  --model humanoid_jetson_deploy/policy.onnx \
  --port /dev/ttyACM0 --baud 921600 \
  --command-source fixed \
  --vx 0.4 --wz 0.5 --walk-seconds 8 --enable-motors \
  --no-plot --max-seconds 20
```

| 参数 | 说明 |
|---|---|
| `--command-source fixed` | 不接 UDP，恒定发 vx/wz |
| `--vx 0.4 --wz 0.5` | **最坏组合**：v/ω = **0.8 m 半径**，一圈 5.03 m / **12.6 秒** |
| `--wz` 符号 | `+0.5` 左转（逆时针），`-0.5` 右转（顺时针） |
| `--walk-seconds 8` | 8 秒后**自动置零**（急停保险），约 2/3 圈。跑整圈改 14 |
| `--max-seconds 20` | 到点进程退出并 `send_disable`（关电机） |

**先 kill 掉 A、B**，不然视觉白占 CPU：

```bash
pkill -f run_policy_vision.py; pkill -f connector.py
```

**读实际转速**（策略到底转没转到位）：

```bash
tail -f logs/motor_positions/motor_positions_*.csv | awk -F, '
NR>1 { y=$NF+0; t=$2+0
  if (pt>0 && t>pt) { d=y-py
    if(d>3.14159)d-=6.28319; if(d<-3.14159)d+=6.28319
    printf "%.2fs  yaw=%+.3f  |wz|=%.3f rad/s  (指令 0.500)\n", t, y, d/(t-pt) }
  pt=t; py=y }'
```

预期 `|wz| ≈ 0.5`。差得多 → 策略执行不了这个转速，视觉那边给满了也还是转不过来。

实测转弯半径 **R = 0.4 / |wz|**；0.5 对应 0.8 m，和赛道中线 0.776 m 只差 2.4 cm。

**扫一遍找拐点**：

```bash
for W in 0.2 0.35 0.5; do
  echo "=== wz=$W ==="
  python -u humanoid_jetson_deploy/main.py --policy walking \
    --model humanoid_jetson_deploy/policy.onnx \
    --port /dev/ttyACM0 --command-source fixed \
    --vx 0.4 --wz $W --walk-seconds 8 --enable-motors \
    --no-plot --max-seconds 20
  sleep 5
done
```

哪个 `wz` 开始出现趔趄/拖步，那个就是步态的拐点。

## 2. 参数表（视觉侧 `run_policy_vision.py`）

| 参数 | 默认 | 作用 |
|---|---|---|
| `--camera` | 0 | 相机索引。**会变，每次按 §0 探测确认** |
| `--vx` | 0.4 | 有有效检测时的前进速度 m/s |
| `--max-wz` | 0.5 | 偏航角速度上限 rad/s，**硬上限 0.5** |
| `--steer-full-scale-cm` | 10 | **多少 cm 横向误差达到满舵**。越小转得越狠 |
| `--yaw-sign` | **1** | 图像→策略的转向符号。**2026-09-25 实车上 -1 是反的**，改成 1 |
| `--step-len-cm` | 8 | 一步走多远，用于前瞻补偿。**必须等于策略的步距** |
| `--preview-gain` | **0** | 航向前馈。**默认 0：`ang` 是曲率信号不是姿态误差，`pg≥3.4` 就把弯道舵打满**（§3） |
| `--bias-cm` | **5** | **弯道内的横向偏置**，补纯比例控制留下的内偏。2026-09-25 实车锁定。换相机安装位置要重测 |
| `--bias-gate-px` | 12 | `\|curve_px\|` 到多少时偏置全量生效。往下渐入到直道的 0 |
| `--shape-every` | **6** | 每多少帧跑一次图卡检测。**很贵，见 §9**。**测图卡时给 2** |
| `--no-shape-detect` | 关 | 关掉图卡检测，`qr` 恒为 -1 |
| `--card-trigger-frac` | **0.5** | **框质心压到画面哪里才停车**（0=顶 1=底）。0.5 = 画面正中。给大了会停得太近 |
| `--card-slow-vx` | 0.2 | 看到图卡之后的前进速度（原来 0.4）。**看到只减速，不停** |
| `--card-clear-calls` | 4 | 连续几次检测不到才清 flag。**这是"每张卡只触发一次"的锁** |
| `--card-hold-ms` | 5000 | 识别出来后保持停车 + 事件有效的时长。**规则要求的动作窗口** |
| `--card-stop-ms` | 3000 | 等分类的**上限**，超时就恢复走（防止卡死站着）|
| `--lost-hold-s` | 0.2 | 丢线后**保持上一个指令**多久再停。单帧漏检不再直接急停 |
| `--deriv-pole` | 0.78 | D 项低通强度。越大越平滑；0 = 只保留中值不加低通 |
| `--headless` | 关 | SSH 下必开 |
| `--max-seconds` | 0（不限） | 自停上限，**建议永远给** |
| `--connector-port` | 5006 | 连接器端口，改了 A 也要改 |

## 3. 推荐值（从赛道几何推出来的，不是试出来的）

### 赛道真实几何

轨道是**体育场形**（stadium）——两端各一个 180° 半圆，其余是直道，底部中间
收窄成限宽门。

| | 半径 | 怎么量的 |
|---|---|---|
| 外边界线两端 | **951 mm** | 对 1:1 渲染图做圆拟合，残差 0.1 px |
| 内边界线两端 | **601 mm** | 同上 |
| 差 | **350 mm** | = 道宽 ✓ 互证 |
| **中线** | **776 mm ≈ 0.78 m** | (951+601)/2 |

> 两个独立来源互证：DXF 里内 R=595 ↔ 外 R=945 的两段圆弧**圆心完全重合**，
> 中线 770mm，与渲染图量出的 776mm 一致。
>
> ⚠️ 底部的限宽门处有样条拼接的**折角**，曲率随测量窗口严格成正比
> （51→104→224→525→942），是纯折角特征，**不是能开的弯**，不要按它算。

其余尺寸：全长 6140mm，道宽 350mm，限宽门处两线最近 **228mm**（规则写 240mm）。

### 速度：`--vx` 就定 0.4

R = 0.776 m，0.4 m/s 需要 ω = 0.4 / 0.776 = **0.515 rad/s**，上限 0.5 —— **缺 3%**。
`connector.py:48` 和 `humanoid_jetson_deploy/command_source.py:21` 两处硬夹 ±0.5，
注释写明 `clamps commands to the ranges used during policy training`。

**这 3% 不值得动。** 缺口有多大代价：机器人按 v/ω = 0.8 m 的半径走（中线要 0.776），
两圆相切于入弯点，180° 处相距 **0.8 − 0.776 = 2.4 cm** —— 这就是整段弯里最大的外偏量。
车道半宽 17.5 cm，随便吃。

要真超 0.5，得改上面那两个**运动侧**文件；而且 0.5 是策略训练范围，超了就是喂分布外
输入，策略可能直接输出乱步态。不动。

### 真正的杠杆是 `--steer-full-scale-cm`（fs）

> ⚠️ **这一节 2026-09-24 修过一次，之前全错。**
> `fused_err` 是无量纲的（`near_err_px / 160`，实测 0.05~0.3），但
> `policy_bridge.py` 把它当 cm 用，于是实际增益比标称**小约 50 倍**：
> 弯道里 `wz` 只有 **0.03 rad/s**，而需要 0.45~0.5 —— 机器人物理上转不了弯，
> 只会一直往前走。已修（检测器新增 cm 版 `fused_err_cm`，`fs` 默认 50 → 10）。

`fs` 带单位，单位就是 `steer` 的单位（cm）；只有 `steer/fs` 这个比值无量纲。

```
wz = clip(steer / fs, -1, 1) × max_wz
steer = kp·err + ki·∫err + kd·d(err)/dt + preview_gain·step_len_cm·sin(ang)
        └───────────────── 四项全是 cm ─────────────────┘
⇒ 打满舵所需误差 e ≈ 1.06 × fs
```

| fs | 打满舵所需横向误差 | 评价 |
|---|---|---|
| 15 | 16 cm | 接近车道半宽 17.5cm，转弯迟钝 |
| **9** | **9.6 cm** | **推荐起步值** |
| 6 | 6.4 cm | 更狠，直道可能开始摆 |

### 推荐起步值

```bash
--vx 0.4  --max-wz 0.5  --steer-full-scale-cm 10
```

（全是默认值，不用手打。`fs=9` 只在实车证明直道不摆、转弯仍有余量时才往下调。）

**注意 `steer` 是按"横向误差"的尺度算的，不是横向误差本身** —— 弯道时航向项和
前瞻项都会贡献。所以过弯看日志里的 `wz` 够不够 0.45，不够就继续降 fs。

### `--preview-gain` 默认 0：它会把弯道舵打满

> 2026-09-25 实车 A/B 推翻的。**上一版这一节写的是"pg=4 是正解"，错的。**

```python
steer += preview_gain * step_len_cm * sin(angle_err)
```

`ang` 是**曲率信号，不是"车头歪了"** —— 静止实测：直道 -0.55°，弯道 +21.9°。
那 21.9° 就是"前方 30cm 的线拐走了"的几何必然。

弯道上这一项 = `pg × 8 × sin(22°) = 2.98 × pg` cm，而 `fs = 10cm`：
**`pg ≥ 3.4` 就顶满量程**，P 项失去调节权。

| 实测（同车同赛道，只改 pg，2Hz 日志） | `pg=4` | `pg=0` |
|---|---|---|
| `steer` 打满（≥10cm） | **71%** | 13% |
| `wz` 顶在 ±0.5 | **74%** | 15% |
| 居中时（`\|err\|<2cm`，`ang≈17°`） | steer **+10.16cm** → wz **+0.473** | steer **+0.01cm** → wz **0.000** |

pg=4 那趟有一段**连续 25 秒的冻结状态**：`err=+7.6cm`、`ang=+22°`、`steer=+18.5cm`、
`wz=+0.500` 一动不动 —— 舵一直打满、回路失去纠偏能力，沿左线转圈。
**这就是"完全循左线"的来源。**

pg=0 之后转向全由 P 项给，代价是纯比例控制必然留的稳态内偏。
实测弯道 `err ≈ +5~6cm`，就是"在线内稍微左切"。

### `--bias-cm` 5：补那个内偏 —— **当前锁定值**

```bash
--bias-cm 5      # 默认值，不用手打
```

`err_有效 = err + bias × clamp(|curve_px|/12, 0, 1)` —— **直道完全不动**，弯道渐入。
日志里 `err_eff=` 是加上偏置后的值，`err=` 还是原始值。

值就是实测的那个内偏（弯道 `err ≈ +5~6cm`）。**它是一次赛道标定，不是算法性质** ——
相机安装位置、俯角、赛道几何一变就要重测。

### 待办：弯道模式从来没生效过

`curve_switch_px = 18`，但真实弯道 `|curve_px|` 只有 **9~14**。所以 `curve_mode`
在弯道中段只有 **6%** 为真，反而在近直段误触发 23% —— **跟曲率反相关**。

后果：`JETSON_PID_CURVE_KP/KI/KD` 和 `lookahead_dyn` 的 2.3× 前馈**全程没用上**，
一直跑的是直道档。要修得把 `curve_switch_px` 降到 9 左右，牵动面大，待定。

### 平滑：两层，一手治突变，一手治抖动

> 2026-09-25 加的。之前整条链路**只有 clamp，没有任何滤波**。

**第一层 — 突变**（连接器，`--max-vx-accel 1.0 --max-wz-accel 2.0`）

覆盖三个原本是阶跃的点：起步（0→0.4 一步到位）、丢线（0.4→0 瞬间）、Ctrl+C 停机。

⚠️ **必须落到精确的 `0.0`**：`policy_runner.py:73` 用
`0.0 if np.all(velocity_command == 0.0) else 0.08` —— **精确浮点判等**。
渐近到 1e-9 的滤波器会让机器人"停着却一直迈 8cm 的步子"。`slew_toward` 最后一步
直接返回 target 本身，所以零是精确零。有个测试专门用反向对照盯着这条。

**第二层 — 抖动**（视觉侧，`--deriv-pole 0.78`）

实测把 `steer` 按 PID 分项拆开（真实巡线视频，cm 按真机尺度）：

| 项 | 均值 | 标准差 | **逐帧跳变 std** | 最大跳变 |
|---|---|---|---|---|
| P | 18.84 | 4.54 | 1.43 | 7.50 |
| I | 0.04 | 0.03 | 0.02 | 0.12 |
| **D（原始）** | **0.84** | **5.49** | **5.93** | **27.04** |
| 前瞻 | 0.06 | 3.44 | 2.76 | 13.65 |

**D 项均值只占 4% 有用信号，却是最大的单一噪声源。** 两个结构性原因：对已经 EMA
平滑过的信号再求差分（把残留高频放大回来），以及 `derr=(err-last_err)/dt` 里的 `dt`
是逐帧实测的（视觉帧率 10~25Hz 波动，`dt` 本身就抖 ±30%）。

治法：**3 点中值（挡单帧误检尖刺）+ 一阶低通 + 固定标称周期 0.05s**。

| `--deriv-pole` | steer 逐帧跳变 std | 降幅 | 最大跳变 |
|---|---|---|---|
| 关（旧） | 7.56 | — | 35.05 cm |
| 0（只中值） | 5.12 | −32% | 28.45 |
| 0.5 | 3.73 | −51% | 16.95 |
| **0.78（默认）** | **3.31** | **−56%** | **12.61（−64%）** |
| 0.9 | 3.17 | −58% | 12.47 |

**−56% 几乎吃满"直接删掉 D 项"那 −59% 的收益，但阻尼保住了。** 0.9 只多 2%，不划算。

## 4. 调参流程

看**终端 B** 的日志（0.5s 一条）：

```
[vision -> connector] vx=+0.400 m/s wz=+0.265 rad/s steer=+5.40cm
  err=+6.4cm err_eff=+6.4cm ang=+24.1deg curve=0 curve_px=-11(thr18) far_px=-29 conf=0.983 lost=0
```

| 字段 | 含义 |
|---|---|
| `wz` | 实际发给策略的偏航指令（rad/s）。**过弯要够 0.45，直道要接近 0** |
| `steer` | PID 输出（cm）。接近 ±10 就是打满，再大也是白搭 |
| `err` | 检测器给的横向误差（cm）。**正 = 车在线的左边** |
| `err_eff` | 加上 `--bias-cm` 之后、真正进 PID 的值 |
| `ang` | 拟合线角度。**曲率信号，不是"车头歪了"**（静止实测直道 -0.5°、弯道 +22°） |
| `curve_px` | 远带中心 − 近带中心。**真实弯道 9~14，直道 ≈0** |
| `conf` | 置信度。**<0.5 说明底部锁没锁上，那时的 `err` 不要信** |
| `qr` | **当前看到什么**。只在识别到的那一帧非 -1，之后回 -1——**它是一次观测，不是状态**。动作走的是 `event_id`（§9）|

| 现象 | 原因 | 改什么 |
|---|---|---|
| 过弯 `wz` 到不了 ±0.4 | fs 还没降够 | `--steer-full-scale-cm` 继续往下（9 → 7 → 6） |
| 直道 `wz` 一直在 ±0.5 来回 | 太热 | `--steer-full-scale-cm` 往上调（9 → 12 → 15） |
| 直道左右摆 | 增益太热 | 提 fs |
| 两端半圆往外甩 | 弯中 3% 饱和，最多外偏 2.4cm | 正常现象，不用管；偏得多说明 fs 没降够 |
| 弯道里车压着左线走 | 纯比例控制的稳态内偏 | `--bias-cm` 填日志里那个稳定的 `err`（如 5） |
| 直道也开始偏 | 偏置阀门开太早 | `--bias-gate-px` 往上（12 → 16 → 20） |
| 弯道转过头 | `--bias-cm` 给大了 | 减半；或 `--bias-gate-px` 往上 |
| 直道小幅高频抖动 | D 项残留噪声 | `--deriv-pole` 往上（0.78 → 0.85 → 0.9） |
| 进弯反应变钝 | D 项滤太狠 | `--deriv-pole` 往下（0.78 → 0.5 → 0） |
| 丢线时一顿一顿 | 保持窗口太短 | `--lost-hold-s` 往上（0.2 → 0.3） |
| 丢线后反应太慢 | 保持窗口太长 | `--lost-hold-s` 往下（0.2 → 0.1） |
| 起步/停车太猛 | 加速度上限太高 | `--max-vx-accel` 降到 0.6；转向猛就降 `--max-wz-accel` |
| 机器人朝反方向拐 | 符号反了 | `--yaw-sign` 在 -1 / 1 之间切，重启 B（默认已是 1） |
| `lost` 经常 > 0 | 丢线 | 见 §6 的第 3 条 |

**每次只改一个参数**，否则不知道是哪条起作用。


|---|---|

| `vx` `wz` | 发给连接器的指令。**过弯看 `wz` 够不够 0.45** |
| `err` | 横向误差（cm）。正的 = 车在线的左边 |


|---|---|

## 6. 常见故障

**1. `can't open camera by index`**
相机索引会变，别写死。先跑 §0 的探测脚本确认哪个能出图（2026-09-25 复测是 `--camera 0`）。

**2. `ModuleNotFoundError: No module named 'onnxruntime'`**
**先怀疑 venv 没激活，不是没装包。** 提示符看有没有 `(.venv)`：

```bash
source .venv/bin/activate
which python        # 必须是 ~/jetson_orin_code/.venv/bin/python
```

详见 §0。这个坑 2026-09-25 踩过两次（人和 AI 各一次）。

**3. `OSError: [Errno 98] Address already in use`**
上次的 connector 没退干净：

```bash
sudo ss -lunp | grep 5006      # 看是谁
pkill -f connector.py
```

**4. `qt.qpa.xcb: could not connect to display` + abort**
SSH 下没加 `--headless`。

**5. 机器人不动 / 走走停停**
视觉频率掉了。看日志的 `fps=`：**低于 4 Hz 会被下游 watchdog 判死发零速**。
图卡检测器单帧 ~90ms，是巡线的 3~4 倍，所以它隔 3 帧才跑一次。如果 `fps` 很低，
先确认没有别的程序抢相机或 CPU。

**6. 转弯冲出去**
按 §3/§4 调。先看弯道里日志的 `wz`：
- **`wz` 上不去 0.4** → 降 `--steer-full-scale-cm`（9 → 7 → 6）。另一种可能是**没 pull
  新代码** —— 修单位前 `wz` 只有 0.03 rad/s，怎么调参数都没用。
- **`wz` 到 ±0.5 了还冲出去** → 不是增益问题，是策略执行不了这个转速，只能降 `--vx`
  （但这会让竞速分变少，先确认 `--vx 0.4` 时实际转弯半径是不是 0.8m）。

`--vx` 保持 0.4：弯中 3% 饱和只让机器人外偏 2.4cm，不是冲出去的原因。

**7. 想全部关掉**

```bash
# 顺序：先关策略（它占串口、退出时会关电机），再关视觉，最后连接器
pkill -f "humanoid_jetson_deploy/main.py"; sleep 1
pkill -f "run_policy_vision.py"
pkill -f "connector.py"
```

⚠️ **不要用 `kill -9`**——策略收不到 SIGTERM 就不会发 `send_disable`，**电机会保持使能**。

## 9. 图卡通信

### 三个字段：观测和事件是分开的

| 字段 | 含义 |
|---|---|
| `qr` | **当前看到什么**，`-1` = 没看到。卡一走就回 -1 |
| `event_id` | **一次确认事件**的唯一编号 |
| `event_action` | 那次事件的动作号 1-6 |

**`qr` 是观测，`event_id`/`event_action` 是事件。** 接收端只认事件、按 ID 去重，
所以同一张卡**不可能触发两次**——这是结构上保证的（`shape_actions.py` 的
`seen_event_ids`），不靠调参。

编号来自 `shape_detector.py` 的 `action_map`，和 `connector.py:51` 的合法值域
是同一套（旧二维码时代留下的 1-6）。

### 谁执行哪个动作

| `qr` | 形状 | 动作 | **谁执行** |
|---|---|---|---|
| 1 | 圆形 | 举左手 | **STM32** |
| 2 | 五角星 | 举右手 | **STM32** |
| 3 | 正方形 | 抬左腿（右脚支撑）| **Jetson 单腿 ONNX** |
| 4 | 菱形 | 抬右腿（左脚支撑）| **Jetson 单腿 ONNX** |
| 5 | 十字形 | 举双手 | **STM32** |
| 6 | 三角形 | 左右摇头 | **STM32** |

**手臂和头不在那 12 个关节里**——它们挂在 STM32 上，走单独的串口消息：

| Type | 方向 | 载荷 | 含义 |
|---:|---|---|---|
| 3 | Jetson→STM32 | `<IB` `event_id, action_id` | 上半身请求，**只收 1/2/5/6** |
| 4 | STM32→Jetson | `<IBB` `event_id, action_id, status` | 1接受 2完成 3忙 4非法 5失败 |

Jetson 每 100 ms 重发一次直到确认；STM32 对重复 ID 只回状态、不重启动作。
腿指令的 watchdog 一旦超时，STM32 会中止进行中的上半身动作并回 status 5。

⚠️ **STM32 固件必须支持消息 3/4。** 没烧新固件的话 1/2/5/6 会被拒——
3/4（走 Jetson）和巡线不受影响。

### 链路

```
shape_detector.py → run_policy_vision.py → connector.py → UDP:5005 → main.py
  action 1-6          qr + event_id         原样透传     shape_actions.py
                      事件保 5 秒           不平滑       按 event_id 去重
```

- `connector.py` 明确注释 `qr` 是离散值、**不参与斜率限制**
- 视觉停发或超时，`connector.py` 把 `qr` 复位成 -1
- 掉一帧相机不会丢事件：保持窗口跨帧有效

### 两段式：先认出"有"，停稳了再认"是哪个"

**走路时的抖动会把卡片外框打成 2~3 条断线，四边凑不齐，整个找框通道返回空。**
所以分成两段，因为这两件事难度差一个量级：

| | 什么时候 | 靠什么 | 要求 |
|---|---|---|---|
| **① 有图卡** | 行走中 | `dbg["presence"]`：**一圈细暗边框围出一块亮纸面**（卡片 = 暗边框 + 白纸；巡线被打成实心粗笔，没有亮孔）。时间累积：最近 9 次里 ≥3 次命中，且最近 3 次内必须有 | 只要能认"有"，**不判是哪个** |
| **② 是哪个** | **停下来之后** | 原来的找框+分类（**已调好，不要动**）。停稳后相机不动，每帧都跑而不是每 `--shape-every` 帧 | 5 秒窗口内认出来 |

```
巡线 → 看到图卡（打 flag）→ 减速继续走（不停）
                            ↓  框质心压到画面正中（--card-trigger-frac 0.5）
                          停车（每帧分类）
                            ├─ 认出 → qr=N → 保持 5 秒 → 恢复巡线
                            └─ 3 秒没认出 → 恢复巡线

每张卡只触发一次：flag 要连续 4 次检测都看不到卡才清除。
```

实机四段视频实测：卡帧命中 **7/157 → 142/157**；无卡帧误报 **0/369**。
`13_14` 那段原来 173 帧一次都不触发，现在触发 29 帧、连成一段且正好框住卡片。

⚠️ **时间窗数的是"检测调用次数"，不是视频帧**，所以 `--shape-every` 会改变它的时间尺度：
默认 6 时，9 次的窗口跨约 **1.8 秒**，不是 0.3 秒。**做图卡测试时把 `--shape-every` 调小。**
