# 视觉代码结构与整合说明

> 面向：负责把本仓库的视觉代码**整合进机器人机载静态代码**的 AI / 工程师。
> 目的：说清「有哪些模块、各自干什么、谁引用谁、整合时哪些地方不能想当然」。

---

## 0. 一句话说完

仓库里的视觉部分是**纯 Python + OpenCV**，没有框架、没有模型权重、没有构建步骤。
真正要整合进机器人的只有 **3 个文件**，它们合起来产出 **4 个视觉结果**：

| 输出 | 谁产出 |
|---|---|
| ① 赛道中心线偏差 + 航向角 | `line_detector_v1_warp.py` |
| ② 红条（障碍杆）距离 | `line_detector_v1_warp.py` |
| ③ 窄门 进/出 信号 | `line_detector_v1_warp.py` |
| ④ 几何图卡 → 动作号 1~6 | `shape_detector.py` |

**状态：①②③ 都没问题；④（图卡）刚修好找框，但覆盖不全，见 §8。**

## 3. 引用关系

```
                    config/cameras.json
                            │
                  ┌─────────┴──────────┐
                  ▼                    ▼
        camera_config.load()    camera_config.to_model_z()
                  │                    │
                  ▼                    ▼
   ┌──────────────────────────┐   shape_detector.py ──┐
   │ line_detector_v1_warp.py │   （也 import 了       │
   │  ├ import utils.clamp    │    camera_config）     │
   │  └ import camera_config  │                        │
   │     .distance_calib()    │                        │
   └────────────┬─────────────┘                        │
                │                                      │
                ▼                                      ▼
            run_robot.py  ── import protocol_v2 ──> 串口 → 主控
                            （唯一入口）
```

要点：

- **两个检测器互不引用**，互相独立。
- 两个检测器都**不读** `line_follow_params.json`（那个是给 Webots / OpenMV 的）。
  `line_detector_v1_warp.py` 是**完全自包含**的，参数全是类内硬编码。
- `shape_detector.py` 是唯一 import `camera_config` 的检测器；`line_detector_v1_warp.py` 只在 `__init__` 里**局部 import** 一次 `distance_calib()`，拿不到就退化成"不校正"。
- 两者都依赖 `utils.clamp`。

## 4. 各模块接口

### 4.1 `camera_config.py`

```python
load(profile=None) -> dict
    # 读 config/cameras.json 的 active 段；可用 env CAMERA_PROFILE 覆盖
    # 键：index, width, height, vfov_deg, mount_height_cm, pitch_deg,
    #     distance_calib{a,b}, calibration{...}, profile
    # 读不到时回退内置默认值（不会抛异常）

distance_calib(profile=None) -> (a, b)          # 距离线性校正系数，带缓存
to_true_z(z_est,  profile=None) -> float        # 模型读数 → 地面真值 cm
to_model_z(z_true, profile=None) -> float       # 真值 → 模型读数（反推像素门槛用）
```

⚠️ `cameras.json` 的路径是**相对 `camera_config.py` 自身位置**算的（`../config/cameras.json`）。
整合时若把文件摊平到别的目录，必须改 `_PATH`。

### 4.2 `line_detector_v1_warp.py`

```python
LineDetector(cam_w, cam_h,
             cam_height_cm, cam_pitch_deg, cam_vfov_deg,
             z_calib=None)          # z_calib=(a,b)，不传则自动从 camera_config 读

process(bgr) -> (dev_px, heading_deg, conf, vis_bird, dbg)
    # dev_px      赛道中心偏差（像素，正=中心在右）
    # heading_deg 航向角（度）
    # conf        置信度；<0.15 视为没找到线
    # vis_bird    可视化鸟瞰图（不画图可忽略）
    # dbg         调试字典，见下
```

`dbg` 里几个有用的键：

| 键 | 含义 |
|---|---|
| `red_bar_detected` / `red_bar_z_cm` | 红条是否可见 / 距相机多少 cm（**已标定的真值**） |
| `narrow_gate_dir` | `-1`=进入窄门，`+1`=离开，`0`=无 |
| `start_line_z` | 起跑线距离 cm（0 = 没看到） |
| `binary` / `bird` / `binary_raw` | 中间图（调试窗口用，可去掉） |

**状态机**：这个对象**有内部状态**（平滑滤波、底部锁定、红条确认帧计数、窄门状态）。
**构造一次，循环复用。**每帧 new 一个会丢掉平滑与闩锁，行为完全不同。

### 4.3 `shape_detector.py`

```python
ShapeDetector(stable_frames=3, cooldown_ms=3200, roi_ratio=1.0, debug=False)

update(bgr_or_gray, lane_offset_cm=None) -> (action_number, dbg)
    # action_number: None 或 1~6
    #   1=圆(举左手) 2=五角星(举右手) 3=正方形(抬左腿)
    #   4=菱形(抬右腿) 5=十字(举双手) 6=三角形(左右摇头)
    # lane_offset_cm: 机身相对赛道中心的横向偏差，用于把图卡约束在赛道内
```

同样**有状态**（连续确认计数、冷却、闩锁），构造一次复用。

内部流程：`二值化找框 → 地面方形判据 → 边闭合度验证 → 单应矫正 200×200 → 纯 CV 规则分类`。

### 4.4 `protocol_v2.py`

帧格式 `0x55 0xAA VER MSG FLAGS SEQ TS_MS(4) LEN PAYLOAD CRC16(2)`，CRC = CCITT-FALSE。

```python
VisionProtocolV2()
    .build_frame(msg_type, payload=b"", flags=0, seq=None, ts_ms=None)
    .build_heartbeat(mode_u8, ts_ms=None)
    .build_line_ctrl(mode_u8, conf_u8, lost_u8, route_u8,
                     ex_mm_i16=0, ang_cdeg_i16=0,
                     v_cmd_mmps_i16=0, w_cmd_mradps_i16=0, ts_ms=None)
    .build_event(msg_type, payload, request_ack=True, seq=None, ts_ms=None)
    .build_qr_event(action_id, request_ack=True)
    .build_obstacle_event(present_u8, distance_cm_u8=0, request_ack=True)
    .build_mode_switch_req(target_mode_u8, request_ack=True)
    .build_estop(reason_code=0, request_ack=True)
    .build_ack(orig_seq, orig_msg_type, code=0, ts_ms=None)

StreamParser().feed(chunk) -> [Frame, ...]
模块级解析：parse_line_ctrl(payload) / parse_heartbeat(payload) / parse_ack(payload)

MSG_HEARTBEAT=0x01  MSG_LINE_CTRL=0x02  MSG_QR_EVENT=0x10
MSG_OBSTACLE_EVENT=0x11  MSG_MODE_SWITCH_REQ=0x12  MSG_ACK=0x80
MSG_ROBOT_STATE=0x81  MSG_ESTOP=0xE0
```

`line_ctrl` 载荷 12 字节，顺序：`mode_u8, conf_u8, lost_u8, route_u8,
ex_mm_i16, ang_cdeg_i16, v_cmd_mmps_i16, w_cmd_mradps_i16`。
`route_u8`：1=直行 2=左 3=右 4=微左。

> ⚠️ **`run_robot.py` 目前没有把图卡动作号发出去。** 检测到图卡只是进 `SM_ACTION`
> 状态、把 `steer` 归零停 3 秒，变量 `sm_action` 存了但没进任何帧。
> 整合时必须补上——协议里现成的载体是 `build_qr_event(action_id)`
> （常量名 `MSG_QR_EVENT` 是 2026 规则把二维码改成几何图形之前的遗留，没改名）。

# ★ 构造一次，循环复用

    if not ok:
        break
    dev_px, heading_deg, conf, vis, dbg = ld.process(frame)
    action, sdbg = sd.update(frame, lane_offset_cm=...)
    # → 转成 route 编码，走 protocol_v2 发串口

## 6. 配置来源（只有一个）

**`config/cameras.json`** 是相机参数的唯一真源：

| 键 | 用途 |
|---|---|
| `width` / `height` / `index` | 开相机用 |
| `vfov_deg` | 反推针孔内参（`fx=fy=H/(2·tan(vfov/2))`, `cx=W/2`, `cy=H/2`） |
| `mount_height_cm` / `pitch_deg` | 地面反投影几何 |
| `distance_calib{a,b}` | 距离线性校正，见 §7.5 |
| `calibration{...}` | 棋盘格标定结果，**仅留档**，目前没有代码引用 |

## 7. 整合时最容易踩的坑

### 7.1 `cam_w / cam_h` 必须等于**实际帧尺寸**
`LineDetector` 在构造时就按这对尺寸算好了 IPM 矩阵。喂进去的帧尺寸不匹配 → 透视变换全错，
表现为"能跑但结果莫名其妙"。**用 `cap.get()` 的真实值，不要写死。**

### 7.2 两个检测器必须用**同一份**相机参数
红条距离、图卡距离、图卡触发门槛都来自同一套针孔模型。
两边参数不一致 → 距离读数互相打架。

### 7.3 检测器有状态，别每帧 new
见 §4.2 / §4.3。

### 7.4 别指望改 `line_follow_params.json` 能影响 Jetson 检测器
它只被 `Webots/` 和脚本读。`line_detector_v1_warp.py` 的参数全在类里。

### 7.5 距离是**标定过**的，不是模型裸算的值
底层针孔模型（`cy=图高/2`、`fy` 由 vfov 反推）**系统性低估距离**：
20cm 处 −1.8%、75cm 处 −9.1%。用地面尺子实测拟合出线性校正：

```
Z_true = 1.13233 · Z_est − 2.4862      （RMS 3.92cm → 0.187cm）
```

系数存在 `cameras.json` 的 `distance_calib`，**不要写死在代码里**——会重测。
重测入口：`python scripts/fit_camera_distance.py --write`。

所有对外报的距离（红条 z、起跑线 z、窄门阈值、图卡触发门槛）都是**校正后的真值**。

### 7.6 依赖
只需要 `opencv-python` + `numpy`。没有 torch / onnx / cupy。

## 8. 当前状态：除了图卡都 OK

| 功能 | 状态 | 依据 |
|---|---|---|
| **① 巡线** | ✅ 可用 | 四段机载抖动视频「有中线率」97 / 86 / 77 / 86%，conf 中位 0.46~0.66 |
| **② 红条** | ✅ 可用 | HSV 判红（黑白地板上唯一带色调的东西），距离已标定 |
| **③ 窄门** | ✅ 可用 | 进入 = 红条 ≤70cm；离开 = 红条 <20cm 或起跑线 <50cm |
| **距离读数** | ✅ 已标定 | 尺子实测 20~75cm，RMS 0.187cm |
| **④ 图卡** | ⚠️ **有保留** | 见下 |

### 窄门为什么不再用"宽窄比"

进入判据原来还包含一条"低带比中带窄 13%"的宽度比信号，已弃用。原因：

鸟瞰图的**横向比例尺随行变化**——20cm 处 1cm 真实横向占 4.56px（比标称大 51%），
80cm 处才对齐到 3.02px。后果是一条**等宽**赛道在低带（z≈20~27cm）比中带
（z≈27~35cm）**凭空宽 11%**，而判据要求窄 13%，畸变吃掉了绝大部分余量，
信噪比太差。

而且这条畸变**随相机高度/俯角变化**（`mount_height_cm` 改过 40→30→32.5），
`narrow_gate_exit_ratio` 是按老几何调的值，几何一改就不一定成立。

> 同一个畸变也影响**任何**基于鸟瞰像素宽度做绝对判断的逻辑。要按物理宽度判断，
> 得先在 `_quad_to_ground` 那类反投影里做，不要在鸟瞰像素上做。

### 图卡为什么"有保留"

- **找框**：刚从 1/11 修到 **11/11**（真实图卡照片），571 帧无卡视频 **0 假阳性**。
- **分类**：这 11 张是**同一张三角形卡**，全判对。**另外五种形状（圆/五角星/正方形/菱形/十字）
  没有任何真实照片数据，分类未经验证。**
- **模糊**：机载视频典型帧的模糊量下，近处（≤40cm，也就是触发区间）能扛，
  但这是**单帧**测量；实际的连续累积确认行为没有实测过。
- 合成测试集**不适用** —— 那批图里的图卡是正面画的，不在相机假定的地面平面上，
  地面方形判据会（正确地）拒掉它们。别拿它当回归基准。
